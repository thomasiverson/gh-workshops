GitHub Copilot: Zero to Agents (Agent Host) — Hands-On Lab Guide

Duration: 82 minutes of required in-session hands-on exercises, plus 30–45 minutes of required prework, within a 4-hour 45-minute scheduled workshop Format: Step-by-step lab exercises Audience: Developers with basic Copilot exposure (completions/chat) Repo: microsoft/GitHubCopilot_Customized (OctoCAT Supply)

Lab Overview

This lab guide contains the hands-on exercises from GitHub Copilot: Zero to Agents Workshop (Agent Host). Each lab maps to the canonical workshop guide and builds a Copilot-first, portable customization stack. Complete the labs in order.

Prerequisites

Requirement Details

Prework: Environment Setup (30–45 min before workshop)

Workshop Section: 1 — Welcome, Objectives & Environment Setup

Objective

Prepare and verify the workshop fork before the scheduled session. Do not wait until Section 1 to perform the first clone or dependency installation.

Steps

Step 1: Fork, Clone, and Pin the Tested Starter

# Fork the repo via GitHub UI, then:
git clone https://github.com/<YOUR-USERNAME>/GitHubCopilot_Customized.git
cd GitHubCopilot_Customized
git switch --create workshop-agent-host 71209b7a796c967ec1bfd65dcd5898220750e4e1

Step 2: Install the Workshop-Safe Delegation Agent

Replace .github/agents/ImplementationIdeas.agent.md with:

---
tools: ['search']
description: Explore implementation ideas and prepare bounded delegation briefs for approved variations
---

# Implementation Ideas

Research the problem and solution space, then summarize distinct variations, tradeoffs, affected files, and verification criteria. Wait for the user to approve specific variations.

For each approved variation, produce a bounded, copyable `/delegate` brief. Do not call external tools, create pull requests, or start cloud work. The user owns the explicit delegation step.

Commit the safe profile locally so cleanup cannot restore the upstream write-capable version:

git add .github/agents/ImplementationIdeas.agent.md
git commit -m "Use workshop-safe implementation ideas agent"
git push --set-upstream origin workshop-agent-host
git status --short
git rev-parse HEAD

Record the final command's output as <SAFETY_BASELINE_SHA> for the optional delegation exercise.

Step 3: Install & Build

npm ci
npm run build

Step 4: Start the Application

npm run dev

Step 5: Verify

  • API running at http://localhost:3000 — open Swagger docs at http://localhost:3000/api-docs
  • Frontend running at http://localhost:5137 — open in browser, click "Products"
  • VS Code: Open Command Palette → type "Copilot" → verify extension is active
  • .github/agents/ImplementationIdeas.agent.md has only tools: ['search'] and contains no PR or cloud action
  • git status --short returns no output

Note: If using Codespaces, ensure API port (3000) visibility is set to public to avoid CORS errors.

Success Criteria

  • ✅ Repository is forked and cloned locally
  • ✅ The checkout starts from tested commit 71209b7a796c967ec1bfd65dcd5898220750e4e1
  • ✅ The safe ImplementationIdeas profile is committed on the local workshop branch
  • ✅ npm ci and npm run build completed without errors
  • ✅ API is running on http://localhost:3000
  • ✅ Frontend is running on http://localhost:5137
  • ✅ Copilot extension is active in VS Code

In-Session Checkpoint

At the start of Section 1, run git status --short, verify the intended fork and branch, open http://localhost:3000/api-docs, and open http://localhost:5137. If setup is incomplete, pair with a prepared participant or use facilitator backup evidence.

Lab 1b: Inline Completion + Inline Chat (6 min)

Workshop Section: 1b — Inline Completion & Inline Chat

Objective

Use inline chat to understand selected code, trigger an inline completion from a descriptive comment, and refine the generated code without leaving the editor.

Starting State

  • Lab 1 is complete and the application is running.
  • api/src/routes/headquarters.ts is unchanged from the cloned repository.
  • Git has no uncommitted changes.

Steps

Exercise 1 — Explain and Generate a PATCH Route

  1. Open api/src/routes/headquarters.ts.

  2. Highlight the existing router.put('/:id', ...) handler and open inline chat with Ctrl+I on Windows/Linux or Cmd+I on macOS.

  3. Enter:

    Explain what this method does and call out what happens to fields that are not included in req.body.

  4. Review the explanation and confirm that the current PUT handler replaces the full record.

  5. Place the cursor after the PUT handler and add:

    // Add a PATCH route to update selected fields instead of replacing the entire headquarters record

  6. Wait for Copilot's inline completion and accept only the useful suggestion with Tab.

  7. Confirm the generated handler preserves existing fields by using a merge pattern similar to:

    headquartersList[index] = { ...headquartersList[index], ...req.body };

Checkpoint: A new PATCH handler is present and performs a partial update rather than replacing the full headquarters record.

Exercise 2 — Refine the Route with Inline Chat

  1. Select the generated PATCH handler.

  2. Open inline chat and enter:

    Add validation so headquartersId cannot be changed by PATCH and send 400 when the request body is empty. Keep the Express handler return type void: call res.status(...).json(...); then return; do not return the Response object.

  3. Review the inline diff before accepting it.

  4. If TypeScript reports No overload matches this call, replace any return res.status(...).json(...) statement with res.status(...).json(...); return;.

  5. Verify the PATCH contracts through Swagger at http://localhost:3000/api-docs or equivalent curl commands:

    • Send {"description":"Workshop check","headquartersId":999} to /api/headquarters/1; expect 200, headquartersId: 1, and the original name: "CatTech Global HQ".
    • Send {} to /api/headquarters/1; expect 400.
    • Send {"description":"Workshop check"} to /api/headquarters/9999; expect 404.

  6. Run:

    npm run build

  7. Stop and restart npm run dev after the checkpoint to restore the in-memory seed data.

For the unknown-ID check from a terminal:

curl.exe -i -X PATCH "http://localhost:3000/api/headquarters/9999" -H "Content-Type: application/json" -d '{"city":"Seattle"}'

curl -i -X PATCH "http://localhost:3000/api/headquarters/9999" -H "Content-Type: application/json" -d '{"city":"Seattle"}'

Expected result: Partial updates preserve omitted fields and headquartersId; empty bodies return 400; unknown IDs return 404; the build succeeds.

Exercise 3 — Add Documentation

  1. Place the cursor above the PATCH handler.
  2. Use inline completion or inline chat to add Swagger documentation matching the existing PUT route.
  3. Confirm the documentation describes a partial update, not a full replacement.

Success Criteria

  • ✅ You used inline chat to explain selected code before editing it.
  • ✅ You triggered and reviewed an inline completion from a descriptive comment.
  • ✅ You refined selected code through an inline diff.
  • ✅ The PATCH route preserves existing fields and headquartersId, rejects an empty body, and returns 404 Not Found for an unknown ID.
  • ✅ npm run build succeeds and the API is restarted to restore seed data.
  • ✅ The Swagger documentation describes partial-update behavior.

Troubleshooting and Recovery

  • If no inline completion appears, keep the descriptive comment, press Enter, and pause; if needed, use inline chat with the same instruction.
  • If the generated route diverges from the existing Express style, reject the diff and ask Copilot to follow the neighboring PUT handler.
  • If the API is not running, restart it with npm run dev before running the smoke test.

Restore the Starting State

After the facilitator checks the result, discard only this exercise's changes:

git restore api/src/routes/headquarters.ts

Lab 2: Configure a Copilot Agent Host Session (8 min)

Workshop Section: 2 — Copilot Agent Host Sessions: Harness, Modes, and Workspaces

Objective

Start a Copilot Agent Host session, use Interactive and Plan, identify Autopilot, and explain how the host, harness, model, permissions, environment, and code isolation differ.

Starting State

  • Lab 1 is complete and the application can run in the workshop workspace.
  • VS Code 1.140 or later is signed in to GitHub Copilot.
  • The Copilot Session Target is available and permitted.
  • Start with a new session so the workspace and harness controls are visible.

Control Reference

Control Workshop Selection Purpose
Session Target Copilot Selects the GitHub Copilot SDK harness in Agent Host
Mode Interactive or Plan Controls how Copilot approaches the task
Model Facilitator-approved model Changes reasoning without changing the harness
Permissions Manual Requires approval before unapproved tools run
Code isolation Folder Uses the active checkout and current uncommitted files

Important: Agent Host owns the session; Copilot is the selected harness. The model, mode, permissions, execution environment, and code isolation are separate controls.

Safety boundary: Copilot worktree sessions always use Allow all. Worktrees isolate code changes but are not security boundaries. Agent sandboxing restricts terminal-command file-system and network access only; it does not sandbox file-edit, URL, or MCP tools. Assisted permissions is Experimental. Sandboxing is Preview on macOS, Linux, and WSL2 and Experimental on Windows.

Target Reference

Target Brief Description Controls to Expect
Copilot GitHub Copilot SDK harness in Agent Host Interactive, Plan, Autopilot; portable Copilot customizations
Claude Anthropic Claude Agent SDK harness Claude controls; CLAUDE.md and .claude/rules/ guidance
Codex OpenAI Codex harness Codex controls and AGENTS.md guidance
Local Built-in extension-host harness Transitional Ask, Agent, and Plan workflows
Cloud Remote provider agent working against a GitHub repository Provider, agent, and model selection; pull-request output

Prompt files are deprecated for Agent Host, and Local is scheduled for removal in a future release. Use Local only as a temporary compatibility path when an extension-host dependency requires it.

Steps

Exercise 1 — Configure the Session:

  1. Open Copilot Chat or the Agents window and start a new session.
  2. Select the OctoCAT Supply checkout as the session folder.
  3. Select Copilot, Folder, Interactive, and Manual permissions.
  4. Keep the facilitator-approved model selected.
  5. Enter:
Identify the testing framework and current test files. Cite your evidence, do not modify files, and do not run commands.
  1. Expand References and confirm that no files changed.

Checkpoint: Agent Host owns a Copilot Interactive session, the answer cites repository evidence, and the checkout is unchanged.

Exercise 2 — Plan Mode:

  1. Switch to Plan, or type /plan.
  2. Enter:
Plan comprehensive error handling for the API routes. Preserve current response contracts, identify decisions I need to make, and include tests. Do not implement yet.
  1. Review the scope, affected files, unresolved decisions, and verification steps.
  2. Do not approve implementation.

Checkpoint: A structured plan is visible and no implementation changes have started.

Exercise 3 — Interactive Implementation:

  1. Switch back to Interactive.
  2. If your app is not already running, enter:
Build and run the project
  1. Then enter:
Open the Swagger documentation page for the API

Checkpoint: The API is available on port 3000, the frontend is available on port 5137, and Swagger documentation opens.

Exercise 4 — Choose and Justify the Controls:

  1. Choose one scenario:
    • Explain authentication from the active checkout without edits or commands while preserving uncommitted work.
    • Produce a reviewable multi-file validation plan without implementing it.
    • Run a trusted, bounded mechanical update in parallel from committed state, accepting unattended continuation.
  2. Record your mode, permission level, Folder or New Worktree choice, and sandbox choice or availability.
  3. Give one reason for each selection and name the residual risk. A worktree isolates code changes but is not a security boundary; its Copilot session uses Allow all.
  4. Compare your decision with a partner, then return the workshop session to Interactive + Manual + Folder.

Checkpoint: Your decision connects task risk to the mode, approval, isolation, and sandbox controls instead of treating them as synonyms.

Success Criteria

  • ✅ You can distinguish Session Target, role or mode, model, permissions, and execution environment.
  • ✅ You can explain how harness choice affects supported project guidance, tools, approvals, and workflow.
  • ✅ You can explain the relationship between Agent Host and the Copilot harness.
  • ✅ You can identify Interactive, Plan, and Autopilot.
  • ✅ You can select and justify a mode, permission level, isolation choice, and sandbox posture for a bounded scenario.
  • ✅ You've received an evidence-backed answer in Interactive without changing files.
  • ✅ You've reviewed a Copilot Plan before implementation.
  • ✅ Interactive has run terminal commands and opened the application.
  • ✅ You can explain why permissions, sandboxing, and code isolation are separate.
  • ✅ Your app is running (API on :3000, Frontend on :5137)

Troubleshooting and Recovery

  • If Copilot is unavailable, update VS Code and the Copilot extension, then verify entitlement and organization policy. Use the facilitator recording if access remains blocked.
  • If the mode picker differs, start a new Copilot session and confirm VS Code 1.140 or later.
  • If you selected Autopilot accidentally, stop the turn, inspect any tool activity and changes, then return to Interactive with Manual permissions.
  • If the app is already running and a second start reports a port conflict, keep the existing process and ask Copilot to verify ports 3000 and 5137 instead.

Lab 3: Classify Memory and Create Custom Instructions (12 min)

Workshop Section: 3 — Copilot Memory & Custom Instructions

Why This Matters

Custom instructions are the simplest way to give Copilot durable, reviewable project guidance. Applicable instructions are included in requests so the agent can follow team standards instead of relying only on generic patterns.

Reference: Customization Hierarchy

Layer File Location When Loaded
Custom Instructions .github/copilot-instructions.md Always (every interaction)
Scoped Instructions .github/instructions/*.instructions.md When matching files are active

What Makes Good Instructions?

✅ Good Candidates ✗ Bad Candidates
Coding standards (naming, style) Entire API documentation
Internal framework references Step-by-step tutorials
Architecture patterns to follow Complete code examples
Security requirements (no hardcoded creds) Business logic rules
Testing conventions Long prose explanations

Note: Keep instructions concise. They're loaded on every interaction and consume context window space. Think bullet points, not paragraphs.

Steps

Step 1: Establish a Baseline (Before Instructions)

  1. Open Copilot Chat with the Copilot target and Interactive mode.
  2. Ask the following question and note the response:
Explain how I should add a new API endpoint to this project. Cite evidence and do not modify files or run commands.
  1. Pay attention to: Does Copilot mention Swagger? Does it reference existing patterns? Does it know about the project's entity model structure?

Step 2: Generate Project-Wide Instructions

  1. Run Chat: Open Customizations, or select Configure Chat and open Overview.
  2. Ask Copilot to generate workspace instructions from the repository.
  3. Watch Copilot analyze the architecture, dependencies, build configuration, and conventions.
  4. Review the generated content. It should reference:
    • The project name and tech stack (TypeScript, React, Express)
    • Build commands (npm ci && npm run build)
    • Testing framework (vitest)
    • Project structure and architecture patterns
  5. Save the file to .github/copilot-instructions.md
  6. Open the saved file and read through it — this is Copilot's understanding of your project

Step 3: Create Scoped API Instructions

Scoped instructions activate only when you're editing files that match a glob pattern. This lets you give Copilot different guidance for different parts of the codebase.

  1. Create the directory: .github/instructions/
  2. Create the file .github/instructions/API.instructions.md with the following content:
---
applyTo: "api/**"
---
# API Development Instructions

For REST APIs in this project:
- Use descriptive endpoint naming following REST conventions
- Add Swagger/OpenAPI docs for all API methods
- Implement proper error handling with appropriate HTTP status codes
- Follow the entity pattern established in existing routes
- Include input validation for all POST/PUT endpoints

Note: The applyTo field uses glob patterns. api/** means these instructions load whenever you have any file under the api/ folder open.

Step 3b: Test Scoped Instructions

  1. Open a file in api/src/routes/ (e.g., product.ts)
  2. In Copilot Chat (Copilot + Interactive), enter:
Explain how I should add a new API endpoint to this project. Cite the applicable instructions and existing route patterns. Do not modify files or run commands.
  1. Expand References and confirm the scoped instruction was applied.
  2. Notice how the response references Swagger docs, REST conventions, error handling patterns, and the entity model structure.

Step 4: Classify Memory and Team Guidance

For each example, choose user memory, repository memory, session memory, or version-controlled instructions, then explain why:

Example Expected Scope
"I prefer early returns across my workspaces." User memory
"This repository stays on React 18 until its planned upgrade." Repository memory
"For this chat only, use the workshop branch." Session memory
"Every API route must include reviewed OpenAPI documentation." Version-controlled scoped instructions

Checkpoint: Personal or emerging context may belong in memory; durable team requirements belong in reviewed files committed with the code.

Step 5: Create a Frontend Scoped Instruction (Bonus)

  1. Create .github/instructions/Frontend.instructions.md:
---
applyTo: "frontend/src/**"
---
# Frontend Development Instructions

For React components in this project:
- Use functional components with TypeScript
- Use Tailwind CSS for all styling — no inline styles or CSS modules
- Follow the existing component structure in `frontend/src/components/`
- Use React hooks for state management
- All components should be exported as default exports
  1. Open a file in src/ and ask Copilot about building a new component — observe the Tailwind and TypeScript guidance in the response

Success Criteria

  • ✅ .github/copilot-instructions.md exists in your repo
  • ✅ .github/instructions/API.instructions.md exists with applyTo: "api/**"
  • ✅ You've compared Copilot's responses before and after adding instructions and noticed the difference
  • ✅ References confirms the applicable instruction was included.
  • ✅ You can distinguish user, repository, and session memory from version-controlled team guidance.
  • ✅ You understand that instructions are durable guidance rather than deterministic enforcement.

Lab 4: Migrate a Prompt File to an Agent Skill (12 min)

Workshop Section: 4 — Migrate Prompt Files to Agent Skills

Objective

Convert a Local-only prompt file into a portable Agent Skill, review the generated metadata and workflow, preserve manual-only invocation, and verify that Copilot Agent Host loads it.

Starting State

  • Labs 1–3 are complete.
  • The repository contains .github/prompts/plan.prompt.md.
  • A new Copilot session can be started in the repository.
  • Keep the prompt file until the migrated skill has been reviewed and tested.

Why This Matters

Prompt files are deprecated for Agent Host and are not loaded by the Copilot harness. The migration flow preserves useful workflow content while moving it into the supported Agent Skills format. Prompt frontmatter does not map one-for-one, so every generated skill requires review.

Steps

Exercise 1 — Classify the Legacy Workflow

  1. Open .github/prompts/plan.prompt.md.
  2. Identify its purpose, required inputs, repository references, output format, and read-only constraints.
  3. Decide that the workflow should remain manually invoked because it represents a deliberate planning checkpoint.

Checkpoint: You can explain why this workflow belongs in a skill rather than always-on instructions or a custom agent.

Exercise 2 — Convert the Prompt

  1. Select the Copilot Session Target.
  2. Run Chat: Open Customizations and open Overview.
  3. Choose Migrate Prompt Files → Convert to Skills.
  4. Select plan.prompt.md.
  5. Keep the original prompt when the confirmation dialog offers the choice.
  6. Complete the conversion.
  7. If the generated name conflicts with Copilot's built-in /plan command, rename the folder and name to implementation-plan.

Checkpoint: .github/skills/implementation-plan/SKILL.md exists and the parent folder exactly matches the name field.

Exercise 3 — Review the Generated Skill

  1. Remove or redesign stale Local frontmatter assumptions such as mode, model, or tool lists.
  2. Ensure the description states what the skill does and when to use it.
  3. Add these properties to preserve manual-only invocation:
user-invocable: true
disable-model-invocation: true
  1. Preserve the requirement to produce a plan without modifying project files.
  2. Remove the source prompt's instruction to save /docs/<feature>-ImplementationPlan.md; require the plan in the chat response instead.
  3. Change the architecture reference for the deeper skill location to ../../../docs/architecture.md, then verify it exists.
  4. Replace any React 19 assumption with the version in frontend/package.json (React 18.3.1 at the verified workshop baseline).
  5. Verify every remaining linked repository file exists and uses portable / path separators.

Checkpoint: The skill is self-contained, manually invocable, and explicit about read-only behavior and expected output.

Exercise 4 — Verify in Agent Host

  1. Start a new Copilot + Interactive session with Manual permissions.
  2. Invoke:
/implementation-plan Add supplier search by name and contact person. Register the static /search route before /:id. Identify decisions and compatibility risks. Do not implement.
  1. Expand References and confirm implementation-plan loaded.
  2. Confirm that no project files changed and no commands ran.
  3. Keep the original prompt until your team accepts the migrated skill; the two files do not stay synchronized.

Success Criteria

  • ✅ You can explain why prompt files are migration sources rather than Agent Host destinations.
  • ✅ .github/skills/implementation-plan/SKILL.md exists with a matching folder and name.
  • ✅ The skill has a useful description and no stale Local-only frontmatter assumptions.
  • ✅ disable-model-invocation: true preserves the deliberate manual checkpoint.
  • ✅ References confirms that the skill loaded in a Copilot Agent Host session.
  • ✅ Verification made no project changes.

Troubleshooting and Recovery

  • If Migrate Prompt Files does not appear, confirm the Copilot target is selected and chat.customizations.promptMigration.enabled is enabled.
  • If /implementation-plan does not appear, verify user-invocable is not false, then start a new session.
  • If the skill is not listed in References, verify the file is named SKILL.md, the folder and name match, and the YAML frontmatter parses.
  • If the migrated skill modifies files, strengthen the body with an explicit read-only boundary and repeat verification in a clean session.

Lab 5: Design a Portable Agent Skill (12 min)

Workshop Section: 5 — Design Portable Agent Skills

Objective

Create a project skill with valid metadata, test relevance-based loading, invoke it explicitly when needed, and verify activation through References.

Starting State

  • Lab 4 is complete and Copilot Agent Host is available.
  • The repository may contain the migrated implementation-plan skill.
  • Git is clean or changes from prior labs are understood.

Why This Matters

Agent Skills package detailed workflows, scripts, examples, and resources without loading every procedure into every request. Copilot discovers skill metadata and may load a relevant skill; discovery does not guarantee invocation. Developers can also invoke user-visible skills explicitly.

Skills are an open standard used across supported Copilot surfaces and compatible agents.

Reference: Skills vs Instructions vs Agents

Aspect Custom Instructions Agent Skills Custom Agents
Location .github/copilot-instructions.md .github/skills/*/SKILL.md .github/agents/*.agent.md
Activation Applicable requests Relevance or explicit /name Select as the active role
Best for Standards and architecture Detailed reusable procedures Specialized roles and tool profiles
Can include Markdown guidance Markdown + scripts + resources Instructions + tools + optional model

Rule of thumb: Instructions define standards. Skills package procedures. Custom agents define roles.

Skill File Structure

.github/skills/
└── api-route-creation/
    ├── SKILL.md              # Required — instructions + frontmatter
    ├── route-template.ts     # Optional — example files Copilot can reference
    └── test-template.ts      # Optional — additional resources

Steps

Exercise 1 — Create an API Route Creation Skill

  1. Create the directory structure:
mkdir -p .github/skills/api-route-creation
  1. Create .github/skills/api-route-creation/SKILL.md with the following content:
---
name: api-route-creation
description: Guide for creating new API routes in the Express.js backend.
  Use this when asked to add new endpoints, entities, or REST resources.
---

Follow this process when creating new API routes:

1. **Create the entity model** in `api/src/models/`
   - Follow the TypeScript interface pattern from existing models
   - Include all required and optional fields with proper types

2. **Create the route file** in `api/src/routes/`
   - Follow the pattern from `api/src/routes/product.ts`
   - Implement full CRUD: GET (list), GET (by ID), POST, PUT, DELETE
   - Add proper error handling with try/catch and appropriate HTTP status codes

3. **Register the route** in `api/src/index.ts`
   - Import the new route module
   - Add it to the Express app with the correct base path

4. **Add Swagger documentation**
   - Add JSDoc annotations with @swagger tags on each endpoint
   - Include request/response schemas, parameters, and example values

5. **Create tests** in `api/src/routes/<entity>.test.ts`
   - Follow the pattern from existing test files
   - Test all CRUD operations and error scenarios
   - Use vitest as the test framework

Exercise 2 — Test Relevance-Based and Explicit Invocation

Test both activation paths and inspect References rather than assuming the skill loaded.

  1. Select Copilot + Interactive with Manual permissions.
  2. Enter a prompt that should trigger the skill:
I need to add a new "Warehouse" entity and API endpoints for managing warehouses. Each warehouse has a name, address, city, state, zipCode, and capacity.
  1. Expand References and check whether api-route-creation loaded.
  2. If it did not load, stop the response and invoke it explicitly:
/api-route-creation Create a Warehouse entity with a name, address, city, state, zipCode, and capacity.
  1. Review every proposed tool call before approval.
  2. Check whether the proposed model, route, registration, Swagger documentation, and tests follow the skill.

Checkpoint: References shows the skill for at least the explicit invocation, and the resulting workflow follows its required steps.

Exercise 3 — Create a Second Skill (Bonus)

Create a react-component-creation skill:

mkdir -p .github/skills/react-component-creation

Create .github/skills/react-component-creation/SKILL.md:

---
name: react-component-creation
description: Guide for creating new React components in the frontend.
  Use this when asked to add new pages, UI components, or frontend features.
---

Follow this process when creating new React components:

1. **Create the component file** in `frontend/src/components/` or `frontend/src/pages/`
   - Use functional components with TypeScript (.tsx)
   - Use Tailwind CSS for all styling — no inline styles or CSS modules
   - Export the component as the default export

2. **Add routing** (if it's a page)
   - Add the route to the router configuration
   - Add a navigation link if appropriate

3. **Connect to the API** (if needed)
   - Use fetch or the existing API utility for data fetching
   - Handle loading, error, and empty states
   - Add TypeScript interfaces for API response types

4. **Follow existing patterns**
   - Reference `frontend/src/pages/Products.tsx` for page structure
   - Reference `frontend/src/components/` for reusable component patterns

Test it by asking Copilot: Create a Warehouses page that shows a list of all warehouses with their addresses

Personal Skills

  • Great for personal coding preferences or tools only you use

Success Criteria

  • ✅ You've created .github/skills/api-route-creation/SKILL.md with a complete step-by-step guide
  • ✅ You've tested both relevance-based loading and explicit slash invocation.
  • ✅ References confirms whether the skill loaded.
  • ✅ You understand that discovery does not guarantee invocation.
  • ✅ You can distinguish standards in instructions, procedures in skills, and roles in custom agents.

Troubleshooting and Recovery

  • If the skill is not discovered, verify the parent folder and name match exactly and SKILL.md uses uppercase spelling.
  • If relevance-based loading does not occur, improve the description or invoke the skill explicitly; absence is not necessarily an error.

Lab 6: Create a Custom Agent in Agent Host (10 min)

Workshop Section: 6 — Custom Agents in Agent Host

Why This Matters

Custom agents define reusable roles with focused instructions and tool sets. Use a skill for a reusable procedure and a custom agent when the work needs a specialized role or capability boundary. This lab does not configure authored subagent or handoff fields.

In this lab you'll work with three agents that show a clear progression:

Agent Type Tools Purpose
OctoCATEngineer Workspace worker Search, edit, terminal, problems Full-stack builder
CodeReviewer Read-only codebase, search, usages, problems Reviews code without editing
ImplementationIdeas Planner Workspace search Researches and prepares bounded delegation briefs

Reference: Agent Skills vs Custom Agents

Feature Agent Skills Custom Agents
Location .github/skills/<name>/SKILL.md .github/agents/*.agent.md
Purpose Reusable procedure and resources Specialized role and tool profile
Invocation Relevance or /name Select as the active specialized role
Best for Testing, debugging, deployment Planning, implementation, review, orchestration

Agent Frontmatter Reference

Lab 7: Portable MCP Configuration Core (12 min)

Workshop Section: 7 — Portable MCP Configuration (Playwright + GitHub)

Why This Matters

MCP (Model Context Protocol) extends Copilot with external tools and context. Agent Host natively reads portable workspace .mcp.json and user ~/.copilot/mcp-config.json. VS Code can forward eligible .vscode/mcp.json definitions, but Agent Host does not read that file directly and some interactive or metadata features do not transfer.

  • Playwright — drives a real browser so Copilot can see and interact with your app
  • GitHub — exposes approved issue, PR, and repository tools through GitHub's API; actual tools depend on toolsets, OAuth scopes, policy, and approvals

Prerequisites

  • Your app must be running with npm run dev.
  • The frontend must be reachable from the environment where the Playwright server runs.
  • The repository starts with .vscode/mcp.json so you can practice the migration.
  • Desktop delivery uses a headed browser; remote hosts, containers, and Codespaces require a reachable browser runtime and typically --headless.

Reference: MCP Configuration

The migration should create workspace-root .mcp.json with a top-level mcpServers object:

Server Type How It Works
GitHub HTTP (remote) Connects to api.githubcopilot.com, OAuth authentication
Playwright stdio (local) Runs npx -y @playwright/mcp@0.0.83 --isolated; add --headless for a rehearsed remote path

Steps

Exercise 1 — Migrate and Verify MCP Configuration

  1. Select the Copilot target.
  2. Run Chat: Open Customizations and open Overview.
  3. Choose Migrate MCP Servers.
  4. Review the Migratable and Not migratable groups and inspect compatibility details.
  5. Migrate compatible workspace servers to .mcp.json; keep .vscode/mcp.json during verification.
  6. Open .mcp.json, confirm it uses mcpServers, contains no credentials, and set the Playwright arguments exactly to ["-y", "@playwright/mcp@0.0.83", "--isolated"]. Add --headless only for the rehearsed remote path.
  7. Rename .vscode/mcp.json to .vscode/mcp.json.pre-agent-host and start a new Copilot session.
  8. Run MCP: List Servers and inspect diagnostics/source attribution. Confirm both servers remain available from .mcp.json, not a forwarded VS Code source.
  9. Complete the GitHub OAuth flow only for organization-approved scopes.
