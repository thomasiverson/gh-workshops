Demo 0: Inline Completion + Inline Chat (Section 1b)

Purpose: Demonstrate the fast local workflow: explain selected code, generate a nearby change with inline completion, then refine it through an inline diff.

Duration: 7 min demo + 6 min hands-on = 13 min; reserve 2 min for transition and recovery

After Slide: Inline Chat Refinements

Environment and Data Prerequisites

  • Lab 1 environment setup is complete.
  • The API is running on http://localhost:3000.
  • api/src/routes/headquarters.ts is unchanged from the cloned repository.
  • The facilitator terminal is open at the repository root.
  • Successful-update, empty-body, unknown-ID, and build commands are prepared in terminal history.

Pre-Demo Setup

  1. Open api/src/routes/headquarters.ts.
  2. Locate the existing router.put('/:id', ...) handler.
  3. Confirm Git has no unrelated uncommitted changes.
  4. Keep the Inline Chat Refinements slide available as the backup visual.

Step-by-Step Script

Part A: Explain Before You Edit (2 min)

  1. Highlight the existing PUT handler.

  2. Open inline chat with Ctrl+I on Windows/Linux or Cmd+I on macOS.

  3. Enter:

    Explain what this method does and call out what happens to fields that are not included in req.body.

  4. Visible checkpoint: Copilot identifies that the handler replaces the full record and that omitted fields can be lost.

  5. Talking point: "Use inline chat to verify the behavior in front of you before asking Copilot to change it."

Part B: Generate the PATCH Handler (2 min)

  1. Place the cursor after the PUT handler.

  2. Type this comment slowly:

    // Add a PATCH route to update selected fields instead of replacing the entire headquarters record

  3. Pause for ghost text, review the suggestion, and accept useful parts with Tab.

  4. Visible checkpoint: The generated handler merges the existing record with req.body, using a pattern similar to:

    headquartersList[index] = { ...headquartersList[index], ...req.body };

  5. Talking point: "The nearby PUT handler supplies the local pattern; the comment supplies the new intent."

Part C: Refine and Verify (3 min)

  1. Select the generated PATCH handler and open inline chat.

  2. Enter:

    Add validation so headquartersId cannot be changed by PATCH and send 400 when the request body is empty. Keep the Express handler return type void: call res.status(...).json(...); then return; do not return the Response object.

  3. Show the inline diff and review it before accepting.

  4. Add route documentation with a second inline-chat request:

    Add Swagger documentation for this PATCH route using the same style as the existing PUT route.

  5. Use Swagger or the prepared commands to verify:

    • PATCH /api/headquarters/1 with {"description":"Workshop check","headquartersId":999} returns 200, preserves name, and keeps headquartersId: 1.
    • PATCH /api/headquarters/1 with {} returns 400.
    • The unknown-ID command below returns 404.
    curl.exe -i -X PATCH "http://localhost:3000/api/headquarters/9999" -H "Content-Type: application/json" -d '{"city":"Seattle"}'

    curl -i -X PATCH "http://localhost:3000/api/headquarters/9999" -H "Content-Type: application/json" -d '{"city":"Seattle"}'

  6. Run npm run build, then restart npm run dev to restore the in-memory seed data.

  7. Visible checkpoint: The route preserves omitted fields and the immutable ID, rejects an empty body, returns 404 for an unknown ID, and builds.

  8. Talking point: "Inline chat is a scalpel for local edits. Move to the full Chat view when the task needs broader codebase context or tools."

Hands-On Instructions (6 min)

Direct attendees to Lab 1b: Inline Completion + Inline Chat. Announce checkpoints at three and six minutes:

  • By minute 3: explain the PUT handler and generate the PATCH handler.
  • By minute 5: refine the handler and verify the four contracts.
  • Final minute: add or verify Swagger documentation, then restart the API to restore seed data.

Likely Failure Modes and Recovery

Failure Recovery
No ghost-text completion appears Press Enter, pause, or invoke inline chat with the comment's instruction
Copilot returns Response from an Express handler Change return res.status(...).json(...) to res.status(...).json(...); return;
Generated handler loses the not-found branch Reject the diff and ask Copilot to preserve the neighboring PUT handler's 404 behavior
Smoke test cannot connect Confirm npm run dev is running and port 3000 is available

Backup Plan

If inline features are unavailable, use the three Section 1b deck slides to walk through the explain, generate, and refine sequence. Show the expected merge expression and 404 Not Found result, then let learners read Lab 1b without modifying code.

Reset

After the demo or learner exercise:

git restore api/src/routes/headquarters.ts

Demo 1: Copilot Agent Host Sessions — Harness, Modes, and Workspaces (Section 2)

Objective: Start a Copilot Agent Host session and separate the host, harness, model, mode, permissions, execution environment, and code isolation Duration: 5 min demo + 8 min hands-on = 13 min After Slide: 18

Setup Before Demo

  • App running (npm run dev)
  • VS Code 1.140 or later open with the project
  • Copilot Session Target available and permitted
  • Copilot Chat or Agents window open with a new-session composer
  • Current OctoCAT checkout selected with Folder isolation
  • Interactive mode and Manual permissions selected
  • Git checkout clean so read-only behavior can be verified
  • Backup screenshots or recording of the session controls, References, and Plan review card

Step-by-Step Script

Part A: Name Every Control (1 min)

  1. Start a new session with the OctoCAT Supply folder.
  2. Select Copilot, Folder, Interactive, and Manual permissions.
  3. Point to the model picker without changing it.
  4. Name the layers: Agent Host owns the session; Copilot is the harness; the model reasons; the mode shapes the workflow; permissions control approvals; Folder chooses the checkout.
  5. Talking point: "These controls cooperate, but none is a synonym for another."

Visible checkpoint: Copilot, Folder, Interactive, Manual, and the selected model are simultaneously visible or identified.

Part B: Interactive with an Explicit Boundary (1.5 min)

  1. Enter:

    Explain the API architecture and cite the route, model, and Swagger configuration files you used. Do not modify files or run commands.

  2. Expand References and show the repository evidence.

  3. Confirm git status --short is unchanged.

  4. Talking point: "Interactive can explain or implement. The request supplies the read-only boundary; the mode name alone does not."

Visible checkpoint: References cite repository files and no edits or commands occurred.

Part C: Plan as a Review Checkpoint (1.5 min)

  1. Select Plan, or enter:

    /plan Add input validation to the Product API POST endpoint. Preserve existing clients, identify decisions I need to make, and include verification steps. Do not implement yet.

  2. Show clarifying questions, affected files, decisions, and verification steps.

  3. Do not approve implementation.

  4. Explain that plan approval and later tool approvals are separate decisions.

  5. Talking point: "Plan is a reviewable artifact, not permission to execute every future action."

Visible checkpoint: A reviewable plan exists and the checkout remains unchanged.

Part D: Autopilot and Isolation Are Not Safety Synonyms (1 min)

  1. Show Autopilot in the mode picker without starting it.
  2. Explain that Autopilot auto-approves tools and continues until it determines completion.
  3. Contrast Folder with New Worktree: a worktree isolates code changes but does not restrict commands, network, or files outside it.
  4. Point to sandboxing as the operating-system boundary.
  5. Return to Interactive with Manual permissions.
  6. Sound bite: "Mode controls workflow, permissions control approval, worktrees isolate code, and sandboxing restricts the environment."

Hands-On Instructions (8 min)

Tell attendees:

"Start Copilot in the current folder with Interactive and Manual permissions, then complete Lab 2."

Interactive read-only request:

Identify the testing framework and current test files. Cite evidence, do not modify files, and do not run commands.

Plan (review only; do not start implementation):

Plan comprehensive error handling for the API routes. Preserve current response contracts, identify decisions, and include tests. Do not implement yet.

Interactive implementation (if not already running):

Build and run the project

"Finish by identifying the host, harness, model, mode, permissions, environment, and isolation. Leave the session on Interactive with Manual permissions."

Key Points to Emphasize

  • Session Target, role or mode, model, permissions, and execution environment are separate controls
  • Harness choice affects supported project configuration, tools, approvals, and workflows
  • Agent Host and the Copilot harness are separate concepts
  • Interactive, Plan, and Autopilot are Copilot modes, not models or permission levels
  • Instruction files shape behavior; tests, hooks, and platform controls enforce requirements
  • Folder and worktree choices control where edits land; neither is a sandbox
  • Cloud is an umbrella target; Section 9 covers GitHub Copilot cloud agent specifically

Backup Plan

If Copilot is unavailable or the live task runs long:

  1. Verify VS Code and the Copilot extensions are current, then confirm entitlement and organization policy.
  2. Show prepared screenshots or a recording of the composer controls, References, and Plan review card.
  3. Use the Host, Harness, and Session slide to narrate the architecture.
  4. Let attendees complete the written control-identification portion of Lab 2 without tool execution.

Reset

No project changes should remain. Run git status --short; discard any accidental edits before continuing.

Likely Failure Modes and Recovery

Failure Recovery
Copilot target is unavailable Verify version, entitlement, and policy; use prepared evidence if still blocked
Interactive, Plan, or Autopilot is missing Start a new Copilot session and confirm VS Code 1.140 or later
Read-only request attempts a tool call Deny it, restate the boundary, and explain why intent must be explicit
Autopilot starts accidentally Stop the turn, inspect tool activity and changes, then return to Interactive + Manual
Worktree lacks dependencies or .env Explain committed-state isolation; use Folder for this workshop or configure approved includes
A second dev server reports a port conflict Keep the existing server and verify ports 3000 and 5137

Demo 2: Copilot Memory & Custom Instructions (Section 3)

Objective: Contrast local personal memory with version-controlled team guidance, then show how custom instructions change Copilot behavior Duration: 10 min demo + 12 min hands-on = 22 min; reserve 13 min for concepts, discussion, and recovery After Slide: 27

Setup Before Demo

  • Ensure .github/copilot-instructions.md does NOT exist yet (this is the exercise)
  • Have docs/tao.md ready to reference
  • New Copilot + Interactive session with Manual permissions
  • Record the exact temporary preference text so only that memory is removed after the demo

Step-by-Step Script

Part A: Memory and Scope (4 min)

  1. Open api/src/routes/headquarters.ts and ask for a validation function before adding memory.

  2. Add this temporary preference:

    Remember for this workshop demo only: prefer early returns over nested if-else.

  3. Start a new prompt with the same validation request and compare the style.

  4. Run Chat: Show Memory Files, identify user, repository, and session scopes, and record the exact file path containing the temporary entry.

  5. Visible checkpoint: The exact workshop preference is visible in the recorded local memory file; no secret or customer data is present.

  6. Talking point: "Memory is personal or emerging context. Reviewed team standards belong in source-controlled instructions or skills."

Part B: Generate Instructions (1.5 min)

  1. Run Chat: Open Customizations, or select Configure Chat and open Overview.
  2. Ask Copilot to generate workspace instructions from the repository.
  3. Show Copilot analyzing the repo — it reads package.json, architecture, routes, and tests.
  4. Review the generated file: Should include references to:
    • TypeScript, Express.js, React
    • Project structure (api/, frontend/)
    • Build commands (npm ci && npm run build)
    • Testing framework (Vitest)
  5. Save to .github/copilot-instructions.md
  6. Talking point: "Copilot proposed a version-controlled instruction file from repository evidence. Review it before treating it as the team's guidance."

Part C: Scoped Instructions (1 min)

  1. Create .github/instructions/API.instructions.md:

    ---
applyTo: "api/**"
---
# API Development Instructions

For REST APIs in this project:
- Use descriptive endpoint naming following REST conventions
- Add Swagger/OpenAPI docs for all API methods
- Implement proper error handling with appropriate HTTP status codes
- Follow the entity pattern established in existing routes
- Include input validation for all POST/PUT endpoints

  2. Talking point: "These instructions only activate when you're working in the api/ directory. Different teams, different rules."

Part D: TAO Internal Framework Demo (2.5 min)

  1. Show docs/tao.md briefly — "This is a fictional internal observability framework"

  2. Add to .github/copilot-instructions.md:

    ## Observability Requirements
- Implement logging and monitoring using TAO (TypeScript API Observability)
- Reference: docs/tao.md
- Assume TAO is installed — never add the package
- Use @Measure, @Trace, and @Log decorators for all service methods

  3. Select Copilot + Interactive with Manual permissions.

  4. Enter prompt:

    Add observability to the Supplier route using our internal standards

  5. Show Copilot generating TAO code:

    import { initTAO, observe } from '@tao/core';
import { Measure, Trace, Log } from '@tao/core';

  6. Talking point: "TAO exists only in this workshop's local documentation. The response follows that supplied context, but it still needs human review and build validation."

  7. Acknowledge: "This code won't compile because the package is intentionally absent. Instructions shape context; they do not guarantee a valid dependency or correct code."

Part E: Cleanup — Revert TAO and Temporary Memory (1 min)

  1. Stay in Copilot Interactive with Manual permissions and enter:

    Revert the TAO observability changes you just made to the Supplier route, and remove the "Observability Requirements" section from .github/copilot-instructions.md. The TAO framework is fictional and the code won't compile.

  2. Show Copilot removing the TAO imports, decorators, and the instructions block

  3. Ask Copilot to remove only the exact for this workshop demo only memory and verify it is absent. Do not use Clear All Memory Files.

  4. If model-directed removal fails, run Chat: Show Memory Files, open the recorded memory file, remove only the recorded entry manually, and verify the phrase is absent.

  5. Verify the app compiles (check terminal or npm run build).

  6. Talking point: "Course-correct generated code and local context deliberately. Shared instructions remain reviewable in Git; personal memory remains under the user's control."

Hands-On Instructions (12 min)

"Five steps — take your time:"

  1. Baseline: In Copilot + Interactive, ask the question and note the response:
How should I add a new API endpoint to this project? Explain only; do not edit files or run commands.
  1. Use Chat: Open Customizations → Overview to generate .github/copilot-instructions.md.
  2. Create .github/instructions/API.instructions.md with the applyTo: 'api/**' frontmatter
  3. Compare and classify: Re-ask the baseline question, then classify one user-memory, repository-memory, session-memory, and version-controlled-instruction example
  4. Bonus: Create a Frontend scoped instruction for frontend/src/** with Tailwind and React conventions

"You have 12 minutes. Post a check mark in chat or raise the provided status indicator when the scoped instruction appears in References; use the help channel for blockers."

Key Points to Emphasize

  • Instructions are reviewable project guidance included in applicable Copilot requests
  • Keep them concise (they consume context window on every interaction)
  • The TAO example shows that local instructions and documentation shape context; review and validation are still required
  • Scoped instructions use glob patterns in YAML frontmatter

Backup Plan

If the Customizations Overview generation flow isn't available:

  1. Create .github/copilot-instructions.md manually in Copilot Interactive:

  2. If generation is slow, use the pre-reviewed template and explain how it was validated.

If memory is unavailable or does not recall the preference:

  3. Verify that no temporary memory was written before proceeding.

Demo 4: Design Portable Agent Skills (Section 5)

Objective: Create a portable skill, test relevance-based loading, invoke it explicitly, and verify both paths through References Duration: 5 min demo + 12 min hands-on = 17 min After Slide: 38

Setup Before Demo

  • Remove only .github/skills/code-review-checklist from rehearsal; other migrated skills may remain
  • New Copilot Interactive session with Manual permissions

Step-by-Step Script

Part A: Create a Skill (2.5 min)

  1. Create directory:

    mkdir -p .github/skills/code-review-checklist

  2. Create .github/skills/code-review-checklist/SKILL.md:

    ---
name: code-review-checklist
description: Checklist for reviewing TypeScript and Express.js code.
  Use this when asked to review code, audit code quality, or check
  for security and performance issues.
---

When reviewing TypeScript or Express.js code, follow this checklist:

1. **Security**
   - Check for unsanitized user input in route handlers
   - Verify no hardcoded secrets, API keys, or credentials
   - Ensure proper auth checks on protected routes
   - Look for SQL/NoSQL injection risks in database queries

2. **Input Validation**
   - Confirm all POST/PUT endpoints validate request body fields
   - Check for missing type guards on `req.params` and `req.query`
   - Verify appropriate HTTP status codes for validation failures

3. **Error Handling**
   - Ensure every route has try/catch with meaningful error responses
   - Check that sensitive details are not leaked to clients
   - Verify async errors are properly caught

4. **Performance**
   - Identify N+1 query patterns or unnecessary database calls
   - Check for missing pagination on list endpoints
   - Look for blocking synchronous operations in async handlers

5. **Maintainability**
   - Verify consistent naming conventions
   - Check for DRY violations — duplicated logic to extract
   - Ensure Swagger/OpenAPI annotations are present and accurate

  3. Explain key fields:

    • name: lowercase identifier that must match the parent folder
    • description: what the skill does and when to use it
    • Omitted invocation properties: both users and the model may request this skill

  4. Talking point: "The description makes relevance-based loading possible, not guaranteed. We will verify what actually happened."

Part B: Test Both Invocation Paths (1.5 min)

  1. Start a new Copilot + Interactive session.

  2. Enter prompt:

    Review the product route handler for security and performance issues

  3. Expand References and check whether code-review-checklist loaded.

  4. If it did not load, invoke it explicitly:

    /code-review-checklist Review the product route handler for security and performance issues.

  5. Expand References again and compare the result.

  6. Talking point: "Relevance matching reduces repetition. Explicit invocation gives the developer a deliberate way to request the workflow."

Part C: Community Skills Reference (1 min)

  1. Open browser to github/awesome-copilot (or mention it)
  2. Mention anthropics/skills
  3. Talking point: "Skills are an open standard. You can use community skills or write your own. Check these repos for inspiration."

Hands-On Instructions (12 min)

"Three exercises:"

  1. Create an api-route-creation skill:
mkdir -p .github/skills/api-route-creation

Create a SKILL.md that teaches Copilot how to create new API routes following the project's Express patterns (model, route, register, Swagger, tests).

  1. Test it: Ask Copilot to add a Warehouse entity, inspect References, then invoke /api-route-creation explicitly if needed
  2. Bonus: Create a react-component-creation skill for frontend components (functional components, Tailwind CSS, TypeScript)

"You have 12 minutes. Focus on getting the first skill created and tested."

Key Points to Emphasize

  • Skill discovery does not guarantee invocation; inspect References
  • The description field should be specific about what the skill does and when to use it
  • User-visible skills can be invoked explicitly as slash commands
  • Skills can include scripts and resource files alongside SKILL.md
  • Project skills (.github/skills/) are shared via git; personal skills (~/.copilot/skills/) are local — ~ is your OS home directory (e.g., C:\Users\<username> on Windows, /Users/<username> on macOS)
  • Skills vs Instructions: instructions = always-on rules, skills = conditional procedures

Backup Plan

If relevance-based loading does not occur:

  1. Treat it as the planned teaching path, not a failure.
  2. Invoke /code-review-checklist explicitly.
  3. Confirm the skill in References.
  4. If the command is missing, verify SKILL.md, the matching folder/name, and user-invocable.

Reset

Remove .github/skills/code-review-checklist after the demo so attendees can create it from a clean starting state.
