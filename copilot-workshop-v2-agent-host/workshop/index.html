GitHub Copilot: Zero to Agents Workshop (Agent Host)

Duration: 4 hours 45 minutes scheduled (270 minutes of instruction + one 15-minute break; no lunch) Format: Presentation + Live Demo + Hands-On Audience: Developers with basic Copilot exposure (completions/chat) Focus: Copilot Agent Host, portable customization, and local-to-cloud agent workflows Repo: microsoft/GitHubCopilot_Customized (OctoCAT Supply)

Workshop Overview

This session teaches the forward GitHub Copilot workflow in VS Code: the Copilot harness running in Agent Host. Attendees begin with inline assistance, then learn how Agent Host separates the harness, model, mode, permissions, and execution environment. They build a portable customization stack with memory, instructions, Agent Skills, custom agents, and MCP servers; migrate legacy Local prompt files to skills; continue the same Copilot runtime in the CLI; and close with autonomous cloud agents and GitHub Copilot code review.

Learning Objectives

  • Start a Copilot Agent Host session and distinguish the host, harness, model, mode, permissions, execution environment, and code isolation
  • Select and justify Copilot Interactive, Plan, or Autopilot for a bounded task, including approval and sandbox tradeoffs
  • Use inline completions and inline chat for fast, focused code edits
  • Explain Copilot Memory scopes and distinguish personal context from reviewable team guidance
  • Create custom instructions that encode team standards and internal frameworks
  • Migrate deprecated Local prompt files into portable Agent Skills
  • Design Agent Skills that Copilot can load by relevance or invoke explicitly
  • Build a custom agent with a constrained tool profile and explain how a search-only planner prepares a human-reviewed delegation brief
  • Configure portable MCP servers for browser testing and GitHub integration
  • Use the standalone GitHub Copilot CLI as another surface for the shared Copilot runtime
  • Evaluate when to delegate work to Copilot cloud agent and when to request GitHub Copilot code review

1b. Inline Completion & Inline Chat (15 min)

Key Points

  • Inline completions are Copilot's fastest path: suggestions appear as ghost text directly in the editor while you type
  • Comments, function names, partially written expressions, and nearby code all shape the suggestion
  • Inline chat (Ctrl+I on Windows/Linux, Cmd+I on macOS) is best for small, focused edits in the current file or selection
  • Use inline completion when you know the local change; use the Chat view when you need broader codebase reasoning or multi-file work
  • Always review generated edits before accepting — Copilot accelerates the edit, but you still own the code

Inline Completion vs Inline Chat vs Chat View

Capability Best For Scope Typical Action
Inline Completion Completing code as you type Current file and nearby code Accept ghost text with Tab
Inline Chat Focused edits to selected code Current file or selection Ask, preview, accept changes
Copilot Interactive / Plan modes Explanation, planning, and multi-file work Agent Host session, workspace, and tools Chat-driven workflow

2. Copilot Agent Host Sessions: Harness, Modes, and Workspaces (25 min)

Key Points

  • Agent Host is the dedicated process that owns sessions independently of the VS Code window displaying them
  • An agent harness connects a model to context, tools, permissions, project configuration, and the agent loop
  • For this workshop, select the Copilot Session Target unless an exercise explicitly compares another harness
  • The Copilot harness uses the GitHub Copilot SDK runtime also used by GitHub Copilot CLI and the GitHub Copilot app
  • The model picker is separate from the Session Target; changing the model does not switch harnesses or convert customization formats
  • Interactive, Plan, and Autopilot are Copilot operating modes; they are not model names or permission levels
  • Permissions and sandboxing remain separate from the mode; Autopilot skips approvals and should be used only in a trusted, bounded environment
  • Folder versus worktree controls where changes land; Copilot worktree sessions use Allow all, and a worktree is code isolation rather than a security boundary

UI baseline (verified October 6, 2026): These labels match VS Code 1.140 and the current VS Code agent harness documentation. Availability varies by account, installed providers, authentication, and organization policy.

2b. Copilot Interactive: Context, Tools, and Explicit Boundaries (10 min)

Key Points

  • Agent Host can search the workspace, but explicit outcomes, constraints, evidence, and verification reduce ambiguity
  • Use Add Context, file references, or a selected editor range when a particular artifact must be considered
  • Use Configure Tools to inspect or restrict the tools available to the current agent
  • A read-only request needs an explicit boundary such as "do not modify files or run commands"
  • Inspect References, tool calls, diffs, and command results instead of relying only on the final explanation
  • Slash commands and controls vary by harness; /plan, /skills, and /agents are useful Copilot entry points

A Strong Agent Request

Element Question to Answer Example
Outcome What result do you want? Explain the authentication flow
Scope Which files or systems are in bounds? Use api/src/middleware/auth.ts and its callers
Constraints What must or must not happen? Do not modify files or run commands
Evidence What should support the answer? Cite relevant files and symbols
Verification How will you know it is complete? Identify unhandled failure paths

Context and Tool Controls

Control Use It When
Add Context A specific file, selection, symbol, or previous result must be included
Configure Tools You need to review, enable, or restrict built-in, extension, or MCP tools
References You need to verify which evidence informed the response
Changes You need to inspect edits before committing, merging, or discarding them
Terminal result You need executable evidence that a build, test, or command succeeded

3. Copilot Memory & Custom Instructions (35 min)

Part A: Copilot Memory (10 min)

Key Points

  • Copilot Memory stores preferences and contextual facts that Copilot can recall in later interactions
  • VS Code memory files are stored locally; GitHub-hosted Copilot Memory is a separate repository-scoped system whose availability depends on account and organization settings
  • Memory is useful for lightweight preferences, such as style choices, naming preferences, or review expectations
  • VS Code local memory can appear in user, repository, and session scopes
  • Memory is different from instruction files: memory is recalled by Copilot, while .github/ instruction files are explicit, reviewable, and version-controlled
  • Never store secrets, tokens, credentials, customer data, or sensitive information in memory
  • If GitHub-hosted Copilot Memory is available for your organization, repository memory can also be managed from GitHub repository settings — this is separate from the VS Code local memory tool

Memory vs Instructions

Capability Best For Scope Governance
Memory Lightweight preferences and facts User, repository, session, or available GitHub-hosted repository memory Review memory files/settings; do not store secrets
Project Instructions Durable team standards .github/copilot-instructions.md Version-controlled and code-reviewed
Scoped Instructions File or folder-specific rules .github/instructions/*.instructions.md Version-controlled and activated by applyTo

How VS Code Memory Scope Is Chosen

Copilot infers where to store local memory from your wording and current context. The exact file name may vary, but the scope folder is the important signal:

Phrase Pattern Likely Scope Example Folder
"I prefer..." or "For me..." User memory across workspaces /memories/
"In this project..." or repo-specific context Repository memory for this workspace /memories/repo/
"For this session..." or temporary task context Session memory for the current chat /memories/session/

If two memories land in different folders, that usually means Copilot classified one as a broad user preference and the other as repo-specific context. Use Chat: Show Memory Files to verify placement, then edit, move, or delete entries that landed in the wrong scope.

Part B: Custom Instructions (25 min)

Key Points

  • Custom instructions are the simplest way to provide durable project guidance to Copilot
  • Applicable instructions are loaded into Copilot requests as reviewable, version-controlled context
  • Two types:
    • Project-wide: .github/copilot-instructions.md — applies to all interactions in the repo
    • Scoped: .github/instructions/*.instructions.md — applies only when matching files are active (uses glob patterns in YAML frontmatter)

What Goes in Custom Instructions?

Good Candidates Bad Candidates
Coding standards (naming, style) Entire API documentation
Internal framework references Step-by-step tutorials
Architecture patterns to follow Complete code examples
Security requirements (no hardcoded creds) Business logic rules
Testing conventions Long prose explanations

Rule of thumb: Keep it concise. Instructions are loaded on every interaction — they consume context window.

Key Takeaways

  1. Agent Host owns the session — the Copilot harness, model, mode, permissions, environment, and isolation remain separate choices
  2. Interactive, Plan, and Autopilot serve different risk profiles — permissions and sandboxing still matter in every mode
  3. Memory is local context, not team policy — promote reviewed knowledge into version-controlled instructions or skills
  4. Custom Instructions encode durable standards — internal frameworks, architecture decisions, and file-specific guidance
  5. Agent Skills replace Local prompt-file workflows — skills package portable procedures and can be loaded by relevance or invoked explicitly
  6. Custom agents define specialized roles — combine role instructions with constrained tool profiles
  7. Portable MCP extends Copilot's reach — use .mcp.json instead of building new dependencies on .vscode/mcp.json
  8. Copilot spans surfaces and environments — continue from Agent Host to CLI or delegate independent work to the cloud
