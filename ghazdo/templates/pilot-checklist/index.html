Advanced Security for Azure DevOps Pilot Checklist

Context: Follow-up to the standalone 90-minute demo-led workshop
Status: Planning aid; not approval or evidence of execution
Target: One existing, user-selected Azure DevOps Services project and Azure Repos Git repository

Scope and Approval

  • Confirm the existing organization, project, repository, default branch, and review branch with its owner.
  • Choose Secret Protection, Code Security, or both according to the risks to address.
  • Obtain explicit product/budget-owner approval before Begin billing.
  • Obtain separate approval for pipeline creation and manual execution, including compute.
  • Keep organization-wide and future-repository defaults unchanged.
  • Do not create a sample project/app, add vulnerable code, insert fake secrets, or generate credentials.
  • Use the portal-first setup guide; setup is outside workshop time.

Planning Estimate

  • Use commits present in pushes during the last 90 days, not original commit dates.
  • Count each developer once per product within the same Azure subscription, including protected repositories and linked organizations.
  • Estimate Secret Protection: count ___ × $19/active committer/month = ___.
  • Estimate Code Security: count ___ × $30/active committer/month = ___.
  • Reference examples: same 25 developers using both = $1,225/month; same 20 using both = $980/month.
  • Label this as a USD list-price estimate, not a quote; inspect the actual agreement, taxes, and currency.
  • Budget pipeline usage and any AI features separately.
  • Recheck current pricing and billing rules.

Ownership and Least Privilege

  • Settings owner ___: Advanced Security: Manage settings.
  • Response owner ___: Advanced Security: Manage and dismiss alerts.
  • Investigation owner ___: Advanced Security: Read alerts.
  • Pipeline owner ___; code/dependency-fix owner ___; credential owner ___; cost owner ___.
  • Verify effective access, repository contribution/review rights, and pipeline creation/queueing rights separately.
  • Confirm supported language/build, task policy, hosted tool availability, agent capacity, feeds, and authentication.

Reviewed Manual Pipeline

  • Choose the language example matching the existing repository; it is not universally ready to run.
  • For JavaScript, confirm nodeVersion: 22.x, workingDirectory: '.', and the existing matching lockfile checked by the guard.
  • For .NET, replace both dotnetSdkVersion and solutionOrProject placeholders to match the repository/global.json and Linux-capable build; review configuration: Release and clean/restore/no-incremental build with shared compiler/MSBuild server off.
  • For Java, replace pomPath, confirm javaVersion: 21 is already installed in the image, and review PreInstalled selection before Init Manual and Maven clean compile -DskipTests.
  • Obtain repository-owner approval before lifecycle or build scripts; scan-preparation tests being skipped does not verify remediation.
  • Preserve the customer's .npmrc and other feeds/authentication; do not copy the content repository's Microsoft feed or embed credentials.
  • Keep explicit Init -> restore/build -> Dependency Scanning -> Analyze order.
  • Check trigger: none, pr: none, hosted ubuntu-24.04, and no deploy/startup steps.
  • Review new YAML in a separate branch under normal policies; leave existing CI files/settings unchanged.
  • Recognize that committing YAML can still trigger existing CI; do not bypass or disable policy.
  • Require all helper target/output parameters and an already-existing scratch directory outside any Git checkout; use the setup guide's TEMP example. Existing output must not be overwritten.
  • Treat normal helper verification as extension/existing-project/repository verification only, not a check of product settings, permissions, or capacity.
  • Offline mode warns and reports Verification=NotPerformed. Action fields set to false mean no action was taken, not that existing products or billing are off.
  • Treat helper output as local preparation only; no sign-in, Git operation, activation, pipeline creation, or scan execution.
  • Create the pipeline and run it manually only after approval.

Scans and Response

  • Review Secret Protection historical scanning and push protection separately; do not create credential tests.
  • For a real leak, coordinate revoke/replace, approved cleanup, confirmation, then alert closure.
  • Choose dependency injection or explicit tasks deliberately; verify a pipeline actually executed.
  • Review dependency PR findings through the branch picker in Repos > Advanced Security; use pipeline logs and applicable PR annotations as complementary evidence.
  • Choose CodeQL scheduled default-branch default setup or advanced custom-build/additional-branch setup based on current support.
  • Confirm intended tasks completed and results were published for the relevant branch/configuration.
  • With no findings, confirm execution and result scope; do not equate emptiness with absence of all risk.
  • For dependency/code findings, require owner assignment, reviewed fix/update, relevant tests, and a comparable completed rescan.
  • Do not promise automatic update PRs or automatic finding-based build/merge blocking.

Monitoring, Cleanup, and Expansion

  • Pair Organization settings > Security overview coverage with completed scan evidence and response ownership.
  • Review previous-day measured per-product counts and monthly invoice expectations; track compute separately.
  • No required paid preview demo. Autofix is limited public preview with restricted access and separately billed AI credits.
  • Agree success measure ___; review date ___; expansion gate ___.
  • Agree retained pipeline/product state ___; cleanup owner/date ___.
  • Remove only owner-approved example pipeline/YAML changes, using normal policies; leave existing CI and customer settings unchanged.
  • Confirm any product disablement manually with the owner; do not promise immediate billing reset.
  • Keep environment-specific evidence in the owner's approved system, not in generic workshop files.
