Choose an Example, Not a New Application

The portal-first setup guide controls approval, repository selection, product activation, reviewed YAML, manual pipeline creation/run, verification, and cleanup. These examples do not create a project/app or require participants to log in.

Do not add vulnerable code, fake secrets, credentials, or demonstration fixtures. Use the repository's actual language/build requirements.

Stack Example Required adaptation
JavaScript/TypeScript security-javascript.yml Confirm nodeVersion, workingDirectory, existing matching lockfile, feeds/authentication. No scripts/build by default.

Selecting an example does not establish a tested or successful pipeline in your repository.

Shared Pipeline Contract

  • Separate security pipeline, not a replacement for existing CI.
  • trigger: none and pr: none: manually queue only after owner/budget approval.
  • Hosted ubuntu-24.04; confirm capacity, tool availability, download/network policies, and permissions.
  • Explicit Init -> restore/build -> Dependency Scanning -> Analyze order.
  • No deployment, application startup, new sample app, or automatic product activation.
  • Preserve the customer's own feeds/authentication and normal policies.

Important: Committing new YAML can still trigger existing CI under its normal policies. Leave current CI files/settings unchanged; do not bypass or disable policy.

JavaScript / TypeScript

  • nodeVersion defaults to 22.x; workingDirectory defaults to '.'.
  • Use UseNode@1 with required versionSource: spec and version from nodeVersion.
  • Confirm that version is compatible with the repository, including package-manager expectations.
  • CodeQL Init uses languages: javascript and buildtype: None for no-build analysis.
  • The example's npm lockfile guard precedes npm ci --ignore-scripts; an existing matching npm lockfile and the correct working directory are required.
  • Preserve the repository's .npmrc and approved feed/authentication mechanism. Do not copy this content repository's Microsoft feed into the target.
  • No lifecycle scripts or application build by default. Suppressing scripts is not a sandbox.
  • If an application build is needed, manually adapt and review the command, scripts, tools, permissions, and risks. Do not run lifecycle or build scripts without repository-owner approval. Yarn/pnpm/workspaces also require explicit adaptation; do not run npm commands against an incompatible repository.

Before running: confirmed Node/package-manager choice, matching lockfile, working directory, authenticated feeds, and no unresolved placeholder.

.NET / C#

  • Use UseDotNet@2 with packageType: sdk and an explicit repository-approved SDK version.
  • Replace both dotnetSdkVersion: '<YOUR-DOTNET-SDK-VERSION>' and solutionOrProject: '<YOUR-SOLUTION-OR-PROJECT>' before running. They are not runnable defaults. configuration defaults to Release.
  • Confirm compatibility with global.json, target frameworks, selected solution/project, and hosted Linux tooling.
  • CodeQL Init uses languages: csharp and buildtype: Manual.
  • Keep initialization before clean/restore/no-incremental build so analysis observes the build. The example disables the shared compiler and MSBuild server.
  • Preserve customer NuGet feeds, configuration, and approved authentication. Do not embed credentials.
  • Review clean/restore/build commands and configuration with the repository owner before execution; no deployment. Appropriate tests remain part of remediation verification.

Before running: explicit SDK and solution/project values, supported Linux build, feed readiness, and reviewed clean build.

Java

  • javaVersion defaults to 21. Use JavaToolInstaller@0 with jdkSourceOption: PreInstalled, jdkArchitectureOption: x64, and versionSpec from that parameter.
  • Confirm that the chosen preinstalled JDK is available on ubuntu-24.04 and matches the repository's build requirements.
  • Replace pomPath: '<YOUR-POM-PATH>' with the correct existing Maven POM before running. Review multi-module paths and build context.
  • CodeQL Init uses languages: java and buildtype: Manual.
  • The preinstalled JDK selection task precedes initialization, then Maven clean compile with -DskipTests. The example skips tests for scan preparation and does not deploy; obtain repository-owner approval before build execution.
  • Preserve the customer's Maven settings, feeds, mirrors, and approved authentication.
  • Gradle/Kotlin: the Maven example is not drop-in. Review current CodeQL Java/Kotlin support, choose repository-approved Gradle/JDK versions, and adapt a clean manual build within the Init/Analyze boundary. Review dependency-scanning support for the actual ecosystem.

Before running: explicit POM path, supported JDK/build tool, authenticated feeds, and reviewed clean compilation. Test code fixes separately; skipped scan-preparation tests do not confirm remediation.

Review Checklist

  1. Select the correct existing repository/branch and stack.
  2. Replace all required placeholders and check every parameter value.
  3. Confirm tool versions, hosted availability, working directory, manifests/lockfiles, and clean build.
  4. Preserve customer feeds/authentication and existing CI policies.
  5. Review the new YAML on a separate branch through normal repository policy.
  6. Confirm product activation and pipeline execution approvals separately.
  7. Manually create/run through the portal, then verify all intended tasks and result scope.
  8. With no findings, review successful execution and applicable results; do not insert a vulnerability.
  9. Use the pilot checklist for ownership, cost review, and retained state.

The optional helper requires all target/output parameters and an already-existing directory outside any Git checkout. Normal mode checks the local azure-devops extension and uses cached Azure CLI access only for read-only GET/show verification of the explicit existing project/repository; it does not inspect product settings, effective permissions, or capacity. Offline mode warns and returns Verification=NotPerformed. Action fields set to false mean the helper did not act, not that existing products are off. Local YAML preparation atomically refuses overwrites and does not create a pipeline; review the file and follow the manual portal steps. See its complete contract and TEMP scratch-folder examples.
