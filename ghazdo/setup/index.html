Portal-First Setup for Advanced Security in Azure DevOps

Context: Optional preparation or follow-up for the standalone 90-minute workshop
Format: Owner-led setup in an existing, user-selected repository
Audience: Authorized Azure DevOps settings and pipeline owners
Status: Independently reviewed generic procedure; customer-specific execution and approval remain required

Scope and Safety

The presentation is demo-led: participants need no accounts or setup. Follow this guide before or after it, only if you are authorized to configure the selected repository.

Use an existing Azure DevOps Services organization, project, and Azure Repos Git repository that you choose. Azure DevOps Server and TFVC are outside scope. Do not create a sample project/application or insert vulnerable code, fake secrets, credentials, or test fixtures.

The optional advanced setup adds a separate, manually triggered security pipeline. Leave existing CI files, settings, and policies unchanged. A commit adding YAML can still trigger existing CI under its normal policies, even when the new YAML has trigger: none and pr: none. Plan for those runs; do not bypass or disable policy.

Billable boundaries: Product activation is a manual, owner-approved action. Activating Secret Protection automatically starts repository scanning and enables push protection. Default setups can also start scans automatically. The separate advanced CodeQL/dependency pipeline described here is queued manually after execution approval. Neither this document nor a generated YAML file approves spending.

1. Confirm Prerequisites and Owner Approval

Before changing settings, confirm:

  • An existing organization linked to the intended Azure subscription.
  • The chosen project, repository, default branch, permitted review branch, and remediation owners.
  • Product scope: Secret Protection, Code Security, or both.
  • Written owner/budget approval for product activation and expected pipeline usage.
  • Effective security permissions, checked separately from repository and pipeline permissions.
  • Repository contribution/review rights and permission to create and manually run the security pipeline.
  • Supported language/build mode, agent suitability, hosted parallel-job capacity, permitted tasks/tool downloads, network access, and package feed/authentication readiness.
  • A known working build/dependency restore process and the repository's own manifests, lockfiles, versions, feeds, and policies.
Permission What it allows
Advanced Security: Read alerts View security findings.
Advanced Security: Manage and dismiss alerts Update or close alerts.
Advanced Security: Manage settings Enable products and change configuration.

Effective rights depend on delegation, inheritance, and denies. Do not assume a project role grants every required permission or broaden access just to make setup work.

Checkpoint: An authorized owner has confirmed target scope, effective rights, costs, language/build requirements, feeds, and capacity. If anything is unknown, stop and resolve it before activation or execution.

2. Select and Inspect the Existing Repository

  1. Open your chosen organization in the Azure DevOps portal.
  2. Select the existing project.
  3. In Repos > Files, select the existing Azure Repos Git repository and confirm the intended default branch.
  4. Inspect manifests, lockfiles, solution/project or POM files, working directory, tool versions, feed settings, and existing build instructions.
  5. Inspect existing pipeline and branch policies with the owner so that adding a reviewed YAML commit is understood. Do not change those policies.
  6. Open Project settings > Repos > Repositories > selected repository and verify the scope before touching security settings.

Checkpoint: You can identify the intended repository and supported build process without creating a new app or altering current CI.

3. Activate Only the Approved Products

  1. In the selected repository's settings, inspect the available Secret Protection and Code Security controls.
  2. Select only the owner-approved products; avoid all-repository selections and defaults for future repositories/projects.
  3. Review the displayed estimate against the approved budget and linked subscription.
  4. The authorized settings owner manually confirms Begin billing only after approval. If an existing bundled interface uses Enable, verify the agreement and current configuration before proceeding.
  5. Record the intended retained product state in the owner's approved system.

Secret Protection: Activation starts historical repository scanning and enables push protection automatically. Review their configuration separately. Historical discovery and supported-pattern push blocking are different behaviors; neither guarantees detection of every credential. Do not generate a credential or add a fake secret to test them. For an unexpected real leak, coordinate revoke/replace with the credential owner.

Code Security: Choose scanning configuration deliberately. Product activation alone does not establish dependency or CodeQL scan completion.

  • Dependency default setup injects scanning into relevant pipelines for the default branch and PR builds targeting that branch; a pipeline must execute.
  • CodeQL default setup provides scheduled default-branch scans for supported languages. Organization/project-level default-setup enablement also queues initial scans automatically. It is an alternative to advanced custom setup, not a claim that every build is eligible.
  • This guide's pipeline path uses explicit dependency tasks and advanced CodeQL in a separate manual pipeline. Avoid enabling duplicate default scanning unintentionally; agree on the intended scanning configuration with the owner.

Checkpoint: Only the chosen repository/products are activated, and any ongoing charges are understood. This checkpoint is enablement, not scan completion.

4. Choose and Adapt the Language Example

Use the template selector. These examples require repository-specific adaptation and review before use.

Stack Example Required adaptation
JavaScript/TypeScript security-javascript.yml Confirm nodeVersion, workingDirectory, existing matching lockfile, feeds/authentication. No scripts/build by default.
.NET/C# security-dotnet.yml Set both dotnetSdkVersion and solutionOrProject; review Linux-capable clean restore/build and feeds.
Java security-java.yml Set pomPath, confirm javaVersion is installed in the image, and review Maven clean compile. Adapt Gradle/Kotlin separately.

All examples use trigger: none, pr: none, hosted ubuntu-24.04, and explicit Init -> restore/build -> Dependency Scanning -> Analyze order, with no deployment.

  • JavaScript/TypeScript: nodeVersion defaults to 22.x and workingDirectory to '.'. UseNode@1 requires versionSource: spec and version; CodeQL language javascript, buildtype None. The npm lockfile guard precedes npm ci --ignore-scripts; a matching existing lockfile is required. No scripts/build by default.
  • .NET/C#: Replace both dotnetSdkVersion: '<YOUR-DOTNET-SDK-VERSION>' and solutionOrProject: '<YOUR-SOLUTION-OR-PROJECT>' to match the repository and global.json; confirm a Linux-capable build. configuration defaults to Release. UseDotNet@2 selects packageType: sdk and explicit version. After CodeQL csharp Init Manual, clean/restore/no-incremental build runs with the shared compiler and MSBuild server disabled; no deployment.
  • Java: javaVersion defaults to 21; replace pomPath: '<YOUR-POM-PATH>'. JavaToolInstaller@0 uses versionSpec, jdkSourceOption: PreInstalled, and jdkArchitectureOption: x64; the chosen JDK must already be installed in the image. The tool task precedes CodeQL java Init Manual, then Maven clean compile with -DskipTests; no deployment. Test remediation separately.

These are examples, not universal ready-to-run pipelines. Multi-language repositories need reviewed adaptation. Manual and None are capitalized CodeQL Init task values.

Preserve the customer's .npmrc, NuGet/Maven/Gradle feeds, approved authentication, and build settings. Do not copy the workshop content repository's Microsoft feed into the target repository. Never embed credentials in YAML or workaround logs. Do not run lifecycle or build scripts without repository-owner approval; --ignore-scripts is not a sandbox.

Checkpoint: Every required placeholder, version, path, build command, and feed dependency has been reviewed. Do not run with unresolved placeholders.

5. Inspect and Review the New YAML

  1. Inspect the chosen example locally or in the portal before adding it.
  2. Adapt it to the selected repository. Use the optional local helper below only if useful; it does not replace review.
  3. Prepare a separate reviewed branch under the repository's normal workflow. In Repos > Files, select that branch before adding azure-pipelines-security.yml.
  4. Inspect the complete file and diff. Keep existing CI files/settings unchanged; no deploy/startup steps, credential values, new vulnerable code, or secret fixtures.
  5. Save the change through normal review. A YAML commit can trigger existing CI under existing policies; coordinate with the pipeline owner rather than disabling or bypassing anything.
  6. Have the repository/pipeline owners review the language, tool versions, task inputs, working directory, restore/build, feeds, triggers, and costs. Merge only according to normal approved policies, if that is the intended setup.

Checkpoint: A reviewed security YAML exists on the explicitly selected branch. No pipeline or scan is created merely by preparing the local file.

6. Manually Create and Run the Security Pipeline

Stop unless pipeline creation and execution have been approved, including capacity and budget.

  1. Open Pipelines > New pipeline in the selected project.
  2. Choose Azure Repos Git and the exact existing repository.
  3. Choose Existing Azure Pipelines YAML file, then explicitly select the reviewed branch and azure-pipelines-security.yml.
  4. Review the complete YAML again. If the UI offers Save separately, save without queueing. If it offers Save and run, treat that control as a run action and do not confirm without explicit execution approval.
  5. Use the manual Run pipeline flow when approved. Confirm repository, branch, YAML, and language parameters. Avoid duplicate runs if one was already started by an approved Save and run action.
  6. Do not add schedules, CI/PR triggers, deployment stages, or changes to current CI as part of this example.

Checkpoint: The separate security pipeline uses the intended reviewed file/branch, and any execution was an explicit approved action. trigger: none and pr: none are not guarantees against all existing repository policies or other queueing mechanisms.

7. Verify Execution and Review Alerts

Successful Scan Checkpoints

  1. Confirm pipeline repository, branch, revision, and language/build parameters.
  2. Inspect task outcomes in order: CodeQL Init, tool/dependency restore or clean build, Dependency Scanning, and CodeQL Analyze.
  3. Resolve failed, skipped, or interrupted tasks before reporting scanning as complete. An overall green run is not a substitute for checking the intended tasks and coverage.
  4. Review task logs for successful analysis and result publication without copying sensitive log content into generic docs.
  5. Open the repository's Advanced Security results/alerts hub. Review the relevant secret, dependency, or code-scanning view and its scope. Allow normal result processing; do not immediately queue duplicate scans.

Findings and No Findings

  • Secret alert: identify credential owner; coordinate revoke/replace, approved cleanup, confirmation, then closure.
  • Dependency alert: inspect advisory and direct/transitive path; identify root manifest/lockfile owner; review update, test, and complete a comparable follow-up scan.
  • CodeQL alert: inspect location/data flow and impact; review fix, test, and complete a same-branch rescan with comparable configuration.
  • No findings: confirm completed tasks, branch/configuration, and the applicable result view. Do not add vulnerable code or fake secrets, and do not describe the repository as free of all risk.
  • PR scanning: select the pull-request branch in Repos > Advanced Security to review its dependency findings. Applicable new findings may also appear as PR Overview annotations. Confirm successful task/result submission in pipeline logs; missing annotations alone are not proof that scanning failed.

Scanning does not automatically create dependency-update PRs or block every build/merge. Enforcement needs a separately designed, reviewed, and verified policy.

Checkpoint: The owner can distinguish enabled products, completed scans, findings/no findings, and confirmed remediation.

8. Cleanup and Recovery

Owner-Approved Cleanup

  • Agree whether the separate manual pipeline and selected products remain enabled for the pilot.
  • Retain normal remediation and evidence according to the owner's process. Do not dismiss alerts solely to make the view empty.
  • If the owner decides to remove the example, delete only the agreed pipeline and review removal of its YAML through normal branch policies. Do not remove repository files or existing CI indiscriminately.
  • Product disablement is a separate owner-approved portal action. Confirm repository/product scope and future monitoring needs first. Review measured counts and invoices; do not promise immediate zero cost or counter reset.
  • Leave existing CI, branch policies, customer feeds/authentication, and other repositories unchanged.

Non-Destructive Recovery

Problem Recovery
Wrong target selected Stop before activation/run; reselect the intended existing repository.
Billing approval missing Do not confirm Begin billing or start scans; return to owners.
Permission denied Verify effective rights with the authorized owner; no blanket admin grant.
Placeholder/path/tool mismatch Review and correct the example in the reviewed branch; do not repeatedly queue it.
Feed/restore/build failure Preserve customer settings; resolve authenticated feed access and build compatibility with owners.
No hosted capacity or required tool Wait for approved capacity/tooling; do not weaken policy or assume the helper guarantees readiness.
Task failed or result absent Inspect task completion, branch, language, and result scope; do not label it a clean scan.

Optional Helper: Read-Only Verification and Local Preparation

Prepare-GhazdoPipeline.ps1 only prepares a local azure-pipelines-security.yml. These instructions do not establish implementation-test or target-execution success.

These command examples use Windows with PowerShell 7+ (pwsh), not Windows PowerShell 5.1. Offline preparation needs only PowerShell 7+ and the downloaded helper/templates. Normal mode also requires an already-installed Azure CLI, its azure-devops extension, and cached authorized access; the helper does not install tools or sign in.

Download Without Access to the Workshop Source Repository

Download the PowerShell helper and the chosen example from the template selector. Store them in this local layout outside a Git checkout; no access to a facilitator's source repository is required:

security-setup/
  setup/
    Prepare-GhazdoPipeline.ps1
  templates/
    security-javascript.yml
    security-dotnet.yml
    security-java.yml

Only the selected stack's YAML is required. Keep its exact filename because the helper resolves it relative to its setup folder. Open PowerShell in security-setup. If you already have this workshop's source files, open workshops\ghazdo instead; the same relative commands apply.

Required parameters: organization URL, project, repository, stack (javascript, dotnet, or java), and an already-existing local output directory outside any Git checkout. Replace every target placeholder with the explicit organization/project/repository you chose; no target defaults are used.

Prepare a real scratch folder under $env:TEMP, not in the workshop or target worktree. Its path must not traverse a junction or symbolic link. Use the same PowerShell session below. The helper rejects linked paths and output inside a checkout.

$GhazdoOutputDirectory = Join-Path $env:TEMP ("ghazdo-security-" + [System.IO.Path]::GetRandomFileName())

Create that directory before invoking the helper:

New-Item -ItemType Directory -Path $GhazdoOutputDirectory

Alternatively, choose another already-existing scratch directory outside any Git checkout. Do not point the helper at an existing file you expect it to replace.

From the local folder containing setup and templates, normal mode checks the installed extension and uses cached sign-in only for read-only GET/show verification of the explicit existing project/repository:

.\setup\Prepare-GhazdoPipeline.ps1 `
  -Organization "https://dev.azure.com/<YOUR-ORG>" `
  -Project "<YOUR-PROJECT>" `
  -Repository "<YOUR-REPO>" `
  -Stack javascript `
  -OutputDirectory $GhazdoOutputDirectory

For local generation without target verification:

.\setup\Prepare-GhazdoPipeline.ps1 `
  -Organization "https://dev.azure.com/<YOUR-ORG>" `
  -Project "<YOUR-PROJECT>" `
  -Repository "<YOUR-REPO>" `
  -Stack javascript `
  -OutputDirectory $GhazdoOutputDirectory `
  -Offline

Choose one mode for a given scratch directory; running the second example after the first would be refused because the output already exists. Use -Stack dotnet or -Stack java when appropriate. All five target/output parameters remain required in offline mode.

Helper Boundaries

  • Normal mode checks only the local azure-devops extension and specified existing project/repository through read-only GET/show operations using cached Azure CLI access. It does not sign in or inspect product settings, effective permissions, or capacity.
  • Offline mode emits an explicit warning and returns Verification=NotPerformed. Successful generation does not establish target existence or access.
  • No Azure writes, Git operations, product activation, pipeline creation, or scan execution.
  • Requires an existing, unlinked output directory outside any Git checkout. Atomically refuses to overwrite existing YAML; prepare another scratch directory rather than deleting a file blindly.
  • Output action fields set to false mean the script did not perform those actions. They do not mean that existing products are disabled, billing is off, or a pipeline does not exist.
  • Does not guarantee product permissions, language support, agent capacity, feed access, successful scans, or findings.
  • Review and adapt the generated YAML, then follow the portal/manual steps above.

Local Scratch Cleanup and Interrupted Writes

Inspect the generated YAML before using it. If generation is interrupted or reports a write error, treat any remaining file as unverified and use a new empty scratch directory for the retry. Never assume a partial file is usable or overwrite unrelated output.

After the reviewed YAML is retained where the owner intends, inspect the original scratch path and remove only the generated file if no longer needed:

Get-ChildItem -LiteralPath $GhazdoOutputDirectory -Force

Remove-Item -LiteralPath (Join-Path $GhazdoOutputDirectory "azure-pipelines-security.yml")

Only if the directory is empty, remove the directory itself without recursive deletion:

if (@(Get-ChildItem -LiteralPath $GhazdoOutputDirectory -Force).Count -eq 0) {
  Remove-Item -LiteralPath $GhazdoOutputDirectory
}
