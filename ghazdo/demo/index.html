GitHub Advanced Security for Azure DevOps Demo Scripts

Duration: Five demos, 30 minutes within the 90-minute workshop
Format: Demo-led presentation; authorized read-only walkthroughs or clearly labeled official examples
Audience: Azure DevOps administrators, developers, security engineers, and engineering leads
Target: An existing Azure DevOps Services organization/project/Azure Repos Git repository selected and authorized by its owner
Execution status: Generic procedures; not executed in a target environment during authoring
Notes status: Independently reviewed teaching guidance with documented pacing recommendations; delivery rehearsal still required

Runbook Contract

The workshop guide is canonical. Participants need no accounts, setup, credentials, or repository access. Optional setup belongs in the separate portal-first guide, outside attendee time.

Use completed, authorized evidence instead of waiting for scans. Do not create projects/apps, insert vulnerable code, add fake secrets, generate credentials, deploy an application, or reuse private screenshots. Prefer read-only presentation. Activation requires owner approval and can itself start scanning: Secret Protection starts historical scans automatically, and default setups have automatic execution behavior. Only this guide's separate advanced pipeline is queued manually after approval.

Fallback introduction: “This is an official documentation example. It illustrates the workflow; it is not a result from the selected repository.” Say this before opening an illustration. If no findings exist, demonstrate successful task completion and result review rather than inventing findings.

Shared Preparation

  1. Confirm authorized scope: one existing repository, selected products, product/budget owners, settings owner, pipeline owner, response owners, and intended retained state. Do not treat this runbook as approval.
  2. Check platform and access: Azure DevOps Services/Azure Repos Git only. Verify effective Advanced Security: Read alerts, Manage and dismiss alerts, and Manage settings as appropriate. Check repository and pipeline rights separately.
  3. Check cost: linked Azure subscription; Secret Protection $19 and Code Security $30 per active committer/month at USD list prices. The same 25 developers using both costs $1,225/month; the exercise's same 20 costs $980. Recheck official pricing and the customer's agreement.
  4. Check billing counts: commits present in pushes during the last 90 days; count separately per product within one Azure subscription, including linked organizations. Charges are calculated daily and billed monthly; settings show the previous day's count. Track compute and AI usage separately.
  5. Check language/build readiness: inspect current manifests/lockfiles, approved feeds/authentication, SDK/JDK/Node versions, working directory, task policies, and agent capacity. Select the language-specific example; do not assume universal support. Do not run lifecycle or build scripts without repository-owner approval.
  6. Prepare completed evidence: if the owner separately approves preparation, follow the portal setup and manual-run steps. Confirm execution status, branch, configuration, and results. Prepare reviewed fix/test/follow-up evidence only if it already exists or the repository owner approves normal remediation.
  7. Prepare a safe shared view: do not store private names, URLs, identifiers, credentials, or captured customer results in this generic package. Do not reuse private screenshots. If sharing the live environment is not appropriate, use official examples.
  8. Open all fallback links before delivery. Official illustrations are examples, not proof of target execution. If offline delivery is required, arrange permitted public documentation illustrations or a text-only explanation; no local screenshot asset is assumed.
  9. Plan recovery and cleanup: know who owns failed setup, unexpected exposure, feed issues, pipeline costs, and retained product state. Do not weaken policies or queue repeated runs to rescue a demo.

Optional Local Preparation

Follow the setup guide's TEMP scratch-folder commands. The helper requires all target/output parameters and an already-existing directory outside any Git checkout; it atomically refuses to overwrite output. Normal mode checks only the local azure-devops extension and explicit existing project/repository through read-only GET/show operations using cached sign-in. It does not inspect product settings, effective permissions, or capacity.

Offline mode warns and returns Verification=NotPerformed. Output action fields set to false mean the helper did not act, not that products are disabled or billing is off. It only prepares a local file: no sign-in, Azure writes, Git operations, activation, pipeline creation, or scans. Review/adapt the file, then use the owner-approved manual portal workflow.

1. Enable Security for a Repository (6 min)

Purpose / section: Section 3, Setup and permissions; identify scope, billable approval, permissions, and completed-scan checkpoints.
Prerequisites: Existing authorized repository; linked subscription; approved product scope; appropriate effective rights; agent/language readiness or official configuration examples.
Status: Target-environment walkthrough requires rehearsal.

Pre-Demo Setup

  • Prefer an already configured repository and read-only presentation.
  • Open repository settings, the selected manual pipeline, and completed task evidence if available.
  • Prepare the approval explanation without displaying private approval records.
  • Open official configuration guidance for fallback.

Ordered Actions and Visible Checkpoints

  1. 0:00–1:00: Open Project settings > Repos > Repositories > selected repository. State that this is one existing user-selected repository, not an all-repository change.
  2. 1:00–2:30: Show the intended product choices and cost estimate. Explain Begin billing as an owner-approved billable confirmation. Do not click without explicit approval; no activation is needed during delivery. An existing bundled UI may use Enable.
  3. 2:30–4:00: Explain Read alerts, Manage and dismiss alerts, and Manage settings. Checkpoint: the audience separates investigation, response, and configuration authority.
  4. 4:00–5:00: Show how the separate manual pipeline fits the existing repository. Explain language/build, feed, task-policy, and agent prerequisites. A new YAML commit can still trigger existing CI under normal policies; leave those policies unchanged.
  5. 5:00–6:00: Contrast configuration with successful execution. Checkpoint: product scope, approver, pipeline/branch, completed tasks, and result location. Preparing a local YAML file does not activate products, create pipelines, or execute scans.

Talk Track

“Choose one repository and the products it needs. Review the estimate and approval before activation, then confirm that the required scans actually completed.”

Likely Failures and Recovery

Failure Safe recovery
Approval or settings permission missing Stop before activation; use official configuration and permission guidance.
UI differs Explain the documented scope; verify current labels and agreement after delivery.
Agent/task/capacity unsupported Record the gap and use official examples; do not bypass restrictions.
Empty alerts view Inspect scan completion and scope; an empty view alone proves neither scanning nor absence of risk.

Backup

Use official configuration and permission definitions. Introduce them with the fallback wording.

Reset / Cleanup

No live changes are required. If setup occurred before the session, confirm the owner-approved retained product/pipeline state. Do not disable other repositories or promise immediate zero charges.

Transition: Exercise 2 asks which prerequisites are missing from an incomplete request.

2. See Secret Protection in Action (7 min)

Purpose / section: Section 4, Secret scanning and push protection; distinguish history detection from new-push prevention and explain real-leak response.
Prerequisites: Suitable authorized existing evidence with no credential content exposed, or official secret-scanning illustrations. No live credential or fixture is required.
Status: No detection or revocation outcome is established by this draft.

Pre-Demo Setup

  • Decide before presentation whether a live view is safe. Do not expose credential values or create a new example in the repository.
  • Open official secret-scanning and push-protection guidance.
  • Know the credential/incident owner for unexpected real exposure.

Ordered Actions and Visible Checkpoints

  1. 0:00–1:30: Introduce historical secret scanning using an authorized view or a labeled official example. Show the type of finding and location without displaying the secret.
  2. 1:30–3:00: Compare with the official blocked-push behavior. Checkpoint: participants explain that an alert does not itself prove a blocked push.
  3. 3:00–5:00: Explain real-leak response: coordinate revoke/replace, remove exposed values through the approved process, confirm resolution, then close the alert.
  4. 5:00–6:00: Explain supported-pattern/validation limits. Do not create fake secrets or stronger credential-like strings to force detection.
  5. 6:00–7:00: Ask why deleting the current value or closing an alert cannot invalidate a credential. Checkpoint: the audience names the credential owner and verification requirement.

Talk Track

“Repository scanning finds existing exposures. Push protection helps prevent new ones. If a real credential leaked, work with its owner to revoke or replace it before treating the incident as resolved.”

Likely Failures and Recovery

Failure Safe recovery
No suitable alert or blocking evidence Use official examples; do not manufacture a finding.
Sensitive value appears Stop sharing, notify the incident owner, and follow revoke/replace procedures as appropriate.
Audience asks for bypass commands Explain approved owner-led cleanup; do not demonstrate bypass or history rewrites.
Expected pattern is not detected Explain coverage limits; no credential generation or push experiment.

Backup

Use the official secret-scanning documentation and describe detection versus prevention explicitly. Never describe the illustration as a successful push-protection test in the chosen repository.

Reset / Cleanup

Do not push, authenticate, change credentials, or dismiss alerts during delivery. For unexpected real exposure, coordinate the incident response; do not silently close the alert.

Transition: Exercise 3 orders the response to an already exposed credential.

3. Review and Fix a Dependency Alert (6 min)

Purpose / section: Section 5, Dependency scanning; connect scan execution, dependency ownership, and remediation verification.
Prerequisites: Code Security configuration, completed authorized scan and suitable existing findings if available, or official dependency examples. Reviewed update/tests/rescan are optional evidence, not assumed.
Status: Target restore/scanning and follow-up outcomes require verification.

Pre-Demo Setup

  • Open the chosen default or explicit-task configuration and completed scan evidence.
  • If findings exist, prepare advisory, direct/transitive path, root manifest/lockfile, and owner.
  • Open official dependency-scanning guidance for a labeled fallback.

Ordered Actions and Visible Checkpoints

  1. 0:00–1:00: Show setup choice. Default injection still needs a pipeline run. Explicit tasks support selected pipelines/branches; the optional setup uses a separate manual pipeline.
  2. 1:00–2:00: Show completed dependency task status and applicable branch. Checkpoint: execution is distinguished from enablement.
  3. 2:00–3:30: Review an existing finding's advisory and dependency path, or the official example. Identify the root manifest/lockfile and remediation owner.
  4. 3:30–5:00: Show reviewed update, tests, and comparable follow-up scan if available; otherwise explain these as required next steps without claiming completion.
  5. 5:00–6:00: Show the PR branch picker in Repos > Advanced Security for dependency findings when relevant. Explain that applicable new findings may also appear as PR Overview annotations. Confirm execution through pipeline logs; an absent annotation does not establish an absent scan.

Talk Track

“Find the affected dependency and its owner, review a suitable update, test the application, and confirm the outcome with a completed follow-up scan.”

Likely Failures and Recovery

Failure Safe recovery
No findings Show successful task completion and result review; do not insert vulnerable dependencies.
Task, lockfile, or feed failure Use official examples; resolve with the owner outside session time. Preserve customer feeds/authentication.
PR finding or annotation absent Select the PR branch in the repository hub and confirm successful task/result submission in pipeline logs before claiming missing coverage.
No completed follow-up Describe remediation as unconfirmed; do not infer resolution from an update PR.

Backup

Label the official dependency illustrations as examples. Scanning does not promise automatic dependency-update PRs or automatic build/merge blocking.

Reset / Cleanup

No update or scan is required during presentation. Any normal remediation belongs to the repository owner's reviewed workflow. Leave manifests, lockfiles, feeds, and policies unchanged during delivery.

Transition: Use two minutes for dependency discussion, then introduce CodeQL.

4. Review and Fix a CodeQL Alert (8 min)

Purpose / section: Section 6, Code scanning with CodeQL; choose setup, explain task order, and trace fix evidence.
Prerequisites: Supported language/build choices, appropriate configuration and completed authorized scan, or official CodeQL examples. Agent capacity and feed access must be confirmed before any separate preparation run.
Status: Templates and target execution are not approved by this narrative.

Pre-Demo Setup

  • Open current default/advanced setup guidance and the template selector.
  • Choose the stack matching the existing repository, not a generated sample application.
  • Prepare completed task evidence and a suitable alert if available; do not run vulnerable code.
  • Open official code-scanning guidance and the Init task reference.

Ordered Actions and Visible Checkpoints

  1. 0:00–1:30: Compare scheduled default-branch default setup with advanced setup for custom builds/additional branches. Confirm current language support rather than assuming universal eligibility.
  2. 1:30–3:00: Inspect example order: Init -> restore/build -> Dependency Scanning -> Analyze. All examples are manual with trigger: none, pr: none, and hosted ubuntu-24.04. No deployment.
  3. 3:00–4:00: Show completed task checkpoints or explain them using official references. JavaScript uses None, nodeVersion: 22.x, workingDirectory: '.', and an npm lockfile guard before restore. .NET requires both dotnetSdkVersion and solutionOrProject placeholders replaced to match the repository/global.json and Linux build; configuration: Release, Init Manual, clean/restore/no-incremental build with shared compiler/MSBuild server off. Java requires pomPath replaced; javaVersion: 21 must already be installed in the image, with PreInstalled selection before Init Manual and Maven clean compile -DskipTests. Confirm customer-owned feeds and owner-approved build execution.
  4. 4:00–5:30: Trace a suitable finding's code location/data flow and impact, or use the labeled official example. If no findings exist, show result review without inventing vulnerable code.
  5. 5:30–7:00: Show reviewed fix, relevant tests, and a completed same-branch rescan with comparable configuration if available. Otherwise identify them as uncompleted next steps.
  6. 7:00–8:00: Ask what a proposed pull request alone fails to prove. Checkpoint: participants require review, tests, execution, and result confirmation.

Talk Track

“Choose setup for your branch and build needs. Review the code change, test it, then scan the same branch again with comparable configuration to confirm resolution.”

Likely Failures and Recovery

Failure Safe recovery
Default setup not eligible Consult current support and review advanced setup; do not activate an alternative live.
Tool/input/policy failure Recheck task refs and owner-approved tooling outside session time; do not weaken restrictions.
No completed scan Use official examples and state execution is unverified.
Follow-up is a different branch/configuration Do not use absence there as proof the original finding was fixed.

Backup

Use official CodeQL illustrations and task documentation. State what is an example and what, if anything, is actual completed evidence.

Reset / Cleanup

No live pipeline run, PR merge, application startup, or deployment is required. Retain the owner-approved pipeline/product state and record unresolved evidence outside this generic package.

Transition: Exercise 4 takes three minutes; then use two minutes to explain optional Autofix and one minute for discussion.

Optional Autofix Explanation

Copilot Autofix is a limited public preview with restricted access and separately billed GitHub AI credits. No preview access or paid generation is required. Recheck current availability and pricing before any separately approved use. Suggested changes still need human review, tests, and a rescan.

5. See Security Across Your Organization (3 min)

Purpose / section: Section 7, Rollout and Q&A; connect organizational coverage with scans, ownership, and costs.
Prerequisites: Effective access to the overview and safe shared information, or official overview examples; pilot checklist.
Status: Actual view availability and scope require rehearsal.

Pre-Demo Setup

  • Open Organization settings > Security overview if authorized.
  • Prepare Risk, Coverage, and Alerts, plus completed scan evidence for the chosen repository.
  • Open official security overview guidance. No private-preview views are required.

Ordered Actions and Visible Checkpoints

  1. 0:00–1:00: Show Risk/Coverage/Alerts within effective access, or introduce the official illustration.
  2. 1:00–2:00: Pair one repository's enablement coverage with completed scan evidence. Checkpoint: coverage is not treated as proof of recent execution.
  3. 2:00–3:00: Connect findings to response owners and the pilot checklist. Review measured per-product counts and separate compute/AI costs before expanding.

Talk Track

“Start with one repository, assign people to act on findings, and review both scan results and costs before adding more repositories.”

Likely Failures and Recovery

Failure Safe recovery
View inaccessible or changed Use official overview guidance; verify access afterward without broad grants.
Coverage but no completed scan Say scanning is unverified and return to execution checkpoints.
No alerts or filtered scope Review effective scope and scan evidence; do not conclude no risk.

Backup

Label official overview illustrations as examples, not a customer organization's coverage results.

Reset / Cleanup

Only harmless view filters may need restoration. Do not change organizational settings or assignments.

Transition: Two minutes for the pilot checklist, one minute for a first-repository/owner/budget response, four minutes for Q&A.

End-of-Session Cleanup and Delivery Limits

  1. Confirm no unapproved activation, scan execution, permission change, or CI/policy change occurred.
  2. If optional setup was separately performed, review retained manual pipeline and selected product states with the owner. Product charges may continue while enabled; do not promise an immediate billing reset.
  3. Do not remove security configuration, alerts, or normal remediation work without owner approval. Use the setup guide's recovery and cleanup.
  4. Record actual rehearsal/execution gaps in the owner's approved system. Do not add private identities, URLs, identifiers, or screenshots to the generic package.
  5. Retain the independent review results and rehearse the full delivery. Section 6's multi-stack detail is reference material; inspect the selected stack during the live demonstration. This runbook is not evidence of customer cloud execution.
