GitHub Advanced Security for Azure DevOps Workshop

Duration: 90 minutes, including 10 minutes of exercises and Q&A; no scheduled break
Format: Demo-led customer presentation with four short, no-login paper exercises
Audience: Azure DevOps administrators, developers, security engineers, and engineering leads
Focus: GitHub Secret Protection and GitHub Code Security for Azure DevOps Services, Azure Repos Git
Package context: Standalone workshop; not a curriculum module
Status: Reviewed for publication with documented warnings; customer-environment validation and delivery rehearsal remain required

Workshop Overview

Show how to protect credentials, third-party dependencies, and application code without moving repositories out of Azure DevOps. Participants observe demonstrations, estimate product costs, and make setup and rollout decisions. They do not need accounts, licenses, installations, or access to a repository.

The optional setup guide is for before or after the presentation. It targets an existing organization, project, and Azure Repos Git repository chosen by the user, not a generated project or application. It creates a separate manual security pipeline through reviewed, owner-approved steps, leaving existing CI configuration unchanged.

Learning Objectives

1. Match secret exposure, vulnerable dependencies, and code vulnerabilities to the appropriate product. Section 1 product matrix and classification discussion Correctly classify three risk scenarios.
2. Estimate monthly product costs using active committers. Section 2 billing rules and worked example Exercise 1: the same 20 developers using both products costs $980/month at USD list prices.
3. Identify approval, permissions, agents, and language/build prerequisites. Section 3 setup demonstration Exercise 2: identify cost approval, settings permission, and pipeline readiness as missing prerequisites.

5. Explain dependency scanning setup and verified remediation. Section 5 configuration and alert walkthrough Explain why a pipeline must execute and why an update needs review, tests, and a follow-up scan.
6. Choose CodeQL default or advanced setup and order a manual security pipeline. Section 6 setup comparison, language examples, and alert walkthrough Exercise 4: choose advanced setup for release branches/custom builds and confirm a fix through review, tests, and a same-branch rescan.
7. Plan a repository-level rollout with clear responsibilities and cost review. Section 7 security overview and pilot checklist Closing response identifies a first repository, setup and response owners, and a budget decision.

Prerequisites

Participants: Basic familiarity with Git, pull requests, and Azure DevOps projects; shared-screen access; paper or a local note-taking tool. No participant login or setup.

Facilitator:

  • Select an existing, authorized Azure DevOps Services organization/project/Azure Repos Git repository, or use clearly labeled official documentation examples. Azure DevOps Server and TFVC are outside scope.
  • Obtain product-owner and budget-owner approval before activation or pipeline execution. Use one repository; do not change organization-wide or future-repository defaults.
  • Check effective Advanced Security permissions separately from repository contribution and pipeline permissions.
  • Verify language/build support, agent compatibility, task policies, available capacity, and the repository's own package feeds and authentication.
  • Prefer completed, authorized scans for live walkthroughs. Do not wait for scans during delivery or promise findings.
  • Do not create an application, insert vulnerable code, add fake secrets, or generate credentials for a demonstration. Do not reuse private screenshots.
  • Use official documentation illustrations when live evidence is unavailable. Introduce them as official examples, not executed results.

No customer cloud action or target-environment execution is established by these generic materials. Follow the demo runbook for preparation, checkpoints, recovery, and cleanup. Independent technical, learning/facilitation, and execution-safety reviews are complete; full delivery rehearsal remains required.

2. Pricing and licensing (12 min)

Pacing: Billing rules 4 min; worked example and questions 5 min; Exercise 1 with answer comparison 3 min.

Key Points

Current USD list prices are Secret Protection $19 and Code Security $30 per active committer/month. The pricing and billing sources were checked by the parent near this rewrite; recheck them before customer delivery. These are planning estimates, not quotes.

  • An active committer is a developer whose commits are present in a push made in the last 90 days; the original commit may be older.
  • Within the same Azure subscription, count each developer once per product, even across multiple protected repositories or linked organizations.
  • Count Secret Protection and Code Security separately if their developer groups differ.
  • Charges are calculated daily and billed monthly. Billing settings show the previous day's measured count.
  • Pipeline usage and AI features are separate costs. Agreements, currency, and taxes can change the actual price.

3. Setup and permissions (15 min)

Pacing: Prerequisites 4 min; permissions 3 min; Demo 1 6 min; Exercise 2 with answer comparison 2 min.

Key Points

Use an existing user-selected repository. Confirm its language, build process, manifests/lockfiles, package feeds, and agent needs before selecting a template. The language examples are not universal ready-to-run pipelines.

Use Project settings > Repos > Repositories > selected repository to select the intended product. Review the estimate and Begin billing confirmation. Product activation is a manual, owner-approved billable action; preparing a YAML file does not activate anything. An existing bundled interface may use Enable; inspect the current UI and agreement rather than forcing a change.

Activating Secret Protection starts historical repository scanning automatically and enables push protection. Default scanning setups also have automatic execution behavior; organization/project CodeQL default-setup enablement queues initial scans. The separate advanced CodeQL/dependency pipeline in this guide is queued manually after approval. Do not assume that avoiding the manual Run button prevents all scanning after activation.

Permission What it allows
Advanced Security: Read alerts View security findings.
Advanced Security: Manage and dismiss alerts Update or close alerts.
Advanced Security: Manage settings Enable products and change configuration.

Effective permissions can differ through delegation, inheritance, and denies. Verify them rather than assuming a role is sufficient. Repository contribution, pipeline creation/queueing, feed access, and capacity are separate checks. Do not distribute settings authority merely to enable investigation.

Separate Manual Security Pipeline

The portal-first setup guide covers product selection, language/build adaptation, a reviewed branch, and explicit manual pipeline creation and execution after budget approval.

  • Leave current CI files and settings unchanged.
  • Adding a YAML commit can still trigger existing CI under its normal policies, even when the new security YAML uses trigger: none and pr: none.
  • Do not bypass or disable existing policies to avoid those runs.
  • The optional helper requires all target/output parameters and an already-existing output directory outside any Git checkout. Prepare a scratch folder under $env:TEMP as shown in the setup guide; confirm it is not inside a checkout.
  • Normal mode checks the local Azure CLI azure-devops extension and verifies only the explicit existing project/repository through read-only GET/show operations using cached sign-in. It does not inspect product settings, effective permissions, or capacity.
  • Offline mode warns that verification was not performed and returns Verification=NotPerformed. Action fields reported as false mean the helper did not act, not that existing products are disabled.
  • The helper only prepares local YAML, atomically refuses to overwrite an existing output file, and performs no sign-in, Azure writes, Git operations, activation, pipeline creation, or scan execution.
  • File preparation does not guarantee product permissions, agent capacity, language support, scan completion, or findings.

Demo and Exercise Connection

Demo 1 shows repository selection, the billing gate, permissions, a separate manual pipeline, and completed scan evidence. Prefer a read-only walkthrough of previously approved setup. Without approval, stop before activation or execution.

Run Exercise 2: Before you enable security. Expected decision: wait until cost approval, Advanced Security: Manage settings, and pipeline readiness are confirmed.

Discussion Points

  • How can an analyst investigate alerts without gaining billable settings authority?
  • What distinguishes prepared configuration, enabled protection, and a completed scan?

4. Secret scanning and push protection (15 min)

Pacing: Concepts 4 min; Demo 2 7 min; Exercise 3 with answer comparison 2 min; discussion 2 min.

Key Points

Feature What it does
Secret scanning Finds exposed credentials in repository history.
Push protection Blocks supported secrets before they reach the repository.

Secret Protection repository scanning and push protection are distinct behaviors. Review both settings and evidence; an alert does not establish that a push was blocked. Supported patterns and validation limit detection; neither mechanism finds every credential.

Do not create live credentials, fake secrets, or new repository fixtures for this workshop. Use existing authorized evidence only when suitable for sharing; otherwise use an official example. A blocked push does not undo an exposure that already happened.

For a real unexpected leak, coordinate with the credential owner and incident process:

  1. Revoke or replace the credential to contain exposure.
  2. Remove the exposed value through the approved repository cleanup process.
  3. Confirm the credential no longer works and cleanup is complete.
  4. Close the alert after confirming resolution. Closing it does not revoke the credential.

For an unpushed secret, deleting it only from the latest file may leave it in outgoing commits. Coordinate approved cleanup of all affected unpushed commits; do not demonstrate bypass or history-rewrite recipes.

Demo and Exercise Connection

Demo 2 compares a historical alert with push-protection behavior. When using documentation, label it Official example and describe what it illustrates, not what happened in a customer repository. Explain the response to a real leak without attempting authentication or changing credentials live.

Run Exercise 3: Respond to an exposed secret. Expected order: C, A, D, B.

Discussion Points

  • Why is deleting a credential and closing the alert insufficient after exposure?
  • Which owner can confirm that the credential has been revoked or replaced?

5. Dependency scanning (12 min)

Pacing: Setup choice 4 min; Demo 3 6 min; discussion and checkpoint 2 min.

Key Points and Decision Criteria

Dependency scanning identifies vulnerable third-party libraries used directly by the application and transitively through other packages.

Setup When to use it
Default setup Add scanning to pipelines for the default branch.
Pipeline task Choose the pipelines and branches to scan.
  • Default setup injects dependency scanning into relevant default-branch pipelines and PR builds targeting that branch. A pipeline must run; enabling injection is not a completed scan.
  • Explicit AdvancedSecurity-Dependency-Scanning@1 tasks support selected pipelines/branches and deliberate placement after dependency restore/build.
  • For this optional setup, use explicit tasks in a separate manual security pipeline rather than changing existing CI.
  • Review dependency findings for a pull-request branch in Repos > Advanced Security by selecting that PR branch in the branch picker. Applicable new findings may also appear as PR Overview annotations. Use pipeline logs to confirm execution and supplement result review; missing annotations do not necessarily mean missing scan results.
  • Do not promise native automatic dependency-update PRs. Review a suitable update, preserve manifest/lockfile consistency, test, and scan again.
  • Findings do not automatically imply build failure or merge blocking. Any enforcement needs separately designed, reviewed, and verified policies.

Demo Connection

Demo 3 connects a completed scan to an advisory, dependency path, owning manifest/lockfile, and remediation plan. Use comparable follow-up execution to confirm a reviewed update. If there are no findings, show task completion and the applicable results view; do not fabricate a vulnerability or conclude that all risk is absent.

Checkpoint: Ask whether enabled injection with no pipeline execution means the repository was scanned. Expected answer: no.

Discussion Points

  • How would you distinguish no findings from no successful scan?
  • Who owns an update when the vulnerable library is a transitive dependency?

6. Code scanning with CodeQL (18 min)

Pacing: Setup and language choices 4 min; Demo 4 8 min; Exercise 4 with answer comparison 3 min; optional-feature explanation 2 min; discussion 1 min.

Key Points and Decision Criteria

CodeQL analyzes source code for security vulnerabilities. Check current language support and build requirements for the chosen setup.

Setup When to use it
Default setup Scheduled scans of your default branch, without maintaining a custom scanning pipeline.
Advanced setup Custom builds, additional branches, or specific pipeline requirements.

Default setup provides a scheduled default-branch baseline for supported languages using managed execution. Do not imply that every CodeQL language or custom build works with it.

Advanced setup supports control over branches, builds, agents, queries, and task placement. For the setup guide, the advanced security pipeline is a separate, manually triggered example, not a replacement for existing CI.

Manual Pipeline and Language Selection

All three language examples use trigger: none, pr: none, and hosted ubuntu-24.04, with explicit order:

Init -> restore/build -> Dependency Scanning -> Analyze.

Stack Example Required adaptation
JavaScript/TypeScript security-javascript.yml: UseNode@1, Node 22.x, CodeQL javascript, buildtype None Confirm nodeVersion and workingDirectory; require an existing matching lockfile for npm ci --ignore-scripts.
.NET/C# security-dotnet.yml: UseDotNet@2, CodeQL csharp, buildtype Manual Set dotnetSdkVersion and solutionOrProject; review Linux-capable clean restore/build and feeds.
Java security-java.yml: JavaToolInstaller@0, preinstalled x64 JDK 21, CodeQL java, buildtype Manual Set pomPath, confirm javaVersion is installed in the image, and review Maven clean compile. Adapt Gradle/Kotlin separately.

See the template selector for the parent-provided YAML examples. Manual and None are capitalized Init task values.

JavaScript parameters default to nodeVersion: 22.x and workingDirectory: '.'. UseNode@1 requires versionSource: spec and version. The example checks for an existing npm lockfile before npm ci --ignore-scripts. No lifecycle scripts or application build run by default; do not add or run them without repository-owner approval. Suppressing lifecycle scripts is not a sandbox.

.NET requires replacing both dotnetSdkVersion: '<YOUR-DOTNET-SDK-VERSION>' and solutionOrProject: '<YOUR-SOLUTION-OR-PROJECT>'. Match the repository and global.json, and confirm a Linux-capable build. configuration defaults to Release. UseDotNet@2 selects packageType: sdk and the explicit version. After Init Manual, the example uses clean/restore/no-incremental build with the shared compiler and MSBuild server disabled; no deployment.

Java defaults to javaVersion: 21; replace pomPath: '<YOUR-POM-PATH>' with the existing POM path. The selected JDK must already be installed in the hosted image. The PreInstalled x64 tool-selection task precedes CodeQL Init Manual, followed by Maven clean compile with -DskipTests; no deployment. Scan preparation is not remediation testing: code fixes still require appropriate tests.

Preserve the customer's own feeds, .npmrc, authentication, SDK choices, and policies. Do not copy the workshop content repository's Microsoft feed into a customer repository or put credentials in YAML.

Demo and Exercise Connection

Demo 4 shows setup choices, the language-specific example, completed scan tasks, and an alert's code location/data flow. Confirm remediation through a reviewed fix, tests, and a completed same-branch, comparable-configuration rescan. If no finding exists, demonstrate scan completion and result review instead.

Run Exercise 4: Choose your CodeQL setup. Advanced setup fits release branches and a custom build. A proposed pull request alone does not prove the issue is resolved.

Optional Copilot Autofix Explanation

Copilot Autofix for Azure DevOps is a limited public preview with restricted access. It uses separately billed GitHub AI credits, excluded from product estimates. Explain the capability only; no preview access or paid generation is required. Recheck availability and credit pricing before any separately approved use. Generated changes still need human review, tests, and a rescan.

Discussion Points

  • Which branch and completed execution would confirm that your fix resolved the alert?
  • Which build customization would require review before adopting an example pipeline?

7. Rollout and Q&A (10 min)

Pacing: Demo 5 3 min; pilot checklist 2 min; closing response 1 min; Q&A 4 min.

Key Points

Use Organization settings > Security overview to inspect Risk, Coverage, and Alerts within effective access. Pair enablement coverage with completed scans and response ownership; coverage alone does not prove a recent successful scan. No private-preview view is required.

Start with a Focused Pilot

Use the pilot checklist:

  1. Choose one existing repository and the products it needs.
  2. Agree on the budget, settings owner, pipeline owner, alert responders, and credential owner.
  3. Review language/build choices and a separate manual pipeline before activation and execution.
  4. Confirm completed scans, assign findings, review fixes, test, and scan again.
  5. Review measured per-product counts, pipeline costs, and results before expanding.

Demo 5 connects organizational views to the chosen repository's actual scan evidence. The closing response asks participants to name a first repository, responsible people, and an approval decision.

End with customer takeaways and Q&A: protect secrets, dependencies, and application code; plan costs using active committers; start with one repository and expand after reviewing results.

Discussion Points

  • What would demonstrate enough value to expand beyond the first repository?
  • Which unresolved ownership or budget issue would prevent starting today?
